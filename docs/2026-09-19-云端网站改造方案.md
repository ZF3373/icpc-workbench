# ICPC 工作台 → 可登录云端网站 · 改造方案

> 状态：方案（五项决策已确认，见第六节；待开工）
> 日期：2026-09-19
> 范围：把当前「本地单用户桌面 / 浏览器应用」改造为「多用户、可注册登录、部署在公网的云端网站」

## 一、现状盘点

### 1.1 形态与技术栈

| 层 | 现状 |
|---|---|
| 后端 | Node ≥22.16 + Express 4 + `node:sqlite`（`DatabaseSync`，**同步 API、进程内单连接**），`server/src/index.ts` 单进程启动 |
| 前端 | React 19 + Vite + Ant Design 5，`BrowserRouter` + 13 个页面路由（`client/src/App.tsx`） |
| 桌面壳 | Tauri 2（`desktop/`），壳负责拉起 SEA 打包的 Node 核心、探测端口、加载页面 |
| 存储 | 单文件 SQLite `server/data/icpc.db`；`dataDir` 下另有 `knowledge/annotations.jsonl`、`backups/`、`typst-bin/`、`update-staging/` |
| 部署 | 服务端固定监听 `127.0.0.1`，前端由 Vite dev server 或 Express 静态目录提供 |

### 1.2 已经具备的多用户地基（好消息）

这不是一个「从零补多租户」的项目，schema 早就按多用户预留过：

- `users` 表已存在，`server/src/db/index.ts` 的 `seed()` 已插入 `id=1, username='me'`。
- 下列**用户私有表**已有 `user_id NOT NULL REFERENCES users(id)` 列与索引：
  `platform_accounts`、`sync_runs`、`submission_intents`、`submissions`、`plans`、
  `checkins`、`review_items`、`template_progress`、`custom_templates`、
  `template_categories`、`problem_lists`。
- 下列表是**平台级共享参考数据**，多用户本就该共用，云端无需拆：
  `platforms`、`problems`（约 1.3 万题内置题库）、`problem_keypoints`、
  `knowledge_concept_stats`、`knowledge_queue`。
- 秘密回显已经做了打码（`server/src/routes/settings.ts` 的 `maskSecret` / `maskCookieHeader`），
  接口不会把 API Key / Cookie 原文回传浏览器——这是很好的起点。
- AI 网页抓取已有 SSRF 防护（`server/src/ai/fetch-url.ts`，含 DNS 解析校验与逐跳重定向校验），
  云端暴露面比本地大，这段逻辑正好复用。

### 1.3 挡在路上的硬约束

按改造难度排序：

**① 完全没有认证。**
`server/src/middleware.ts` 只有 `securityHeaders` 与 `errorHandler` 两个中间件，
没有任何身份校验。任何能连上端口的人 = 完整拥有这份数据。

**② 单用户常量散落在 19 个文件。**
`server/src/constants.ts` 定义 `DEFAULT_USER_ID = 1`，被
`adapters/sync.ts`、`adapters/syncScheduler.ts`、`ai/templateContext.ts`、`plans/planService.ts`、
`routes/{ai,checkins,export,import,knowledge,lists,plans,problems,reviews,settings,stats,sync,templates,today}.ts`
引用。这些引用必须全部换成「当前请求的用户」。

**③ `settings` 表是全局 key-value，且装了用户私有数据——这是最大的隔离缺口。**
`server/src/db/schema.sql` 里 `settings(key TEXT PRIMARY KEY, value TEXT NOT NULL)`，
而下列**每个用户都该有自己一份**的配置都写在这张全局表里：

| 键 | 内容 | 敏感度 |
|---|---|---|
| `ai.enabled` / `ai.baseURL` / `ai.apiKey` / `ai.model` / `ai.timeoutMs` / `ai.maxTokens` / `ai.contextWindow` / `ai.searchEngine` / `ai.searchApiKey` | AI 配置 | **高（含密钥）** |
| `cookie.<platform>` / `csrf.<platform>` / `ua.<platform>` | 各平台登录 Cookie | **高（等于账号凭据）** |
| `adapter.<platform>.enabled` | 适配器开关 | 中 |
| `reminder.enabled` / `reminder.time` / `contestReminder.enabled` / `contestReminder.minutesBefore` | 打卡与赛前提醒 | 低 |
| `sync.maxSubmissions` / `sync.autoContinueRounds` / `jisuanke.practiceSync` | 同步偏好 | 低 |
| `knowledge.minConfidence` | 知识点置信度阈值 | 低 |
| `backup.lastDailyAt` / `bank.builtin.version` | 实例级状态 | 应保持全局 |

如果不改这张表，用户 A 保存的洛谷 Cookie 会被用户 B 的同步直接拿去用。

**④ 只监听 `127.0.0.1`。**
`server/src/index.ts:98` 与 `server/src/sea.ts:249` 都写死了回环地址，
且代码注释明确写着「若以后需要远程访问，应单独设计认证和 TLS」——本方案就是这件事。

**⑤ 秘密明文落库。**
AI API Key、Tavily/Brave Key、各平台 Cookie 以明文存在 SQLite 文件里。
本地单机时这是可接受的取舍；一旦放到云端托管**别人的**凭据，明文存储就是不可接受的责任。

**⑥ 备份 / 恢复是「整库文件」模型。**
`server/src/backup.ts` 用 `VACUUM INTO` 做整库快照，
恢复走 `restore-pending.json` + 重启时 `applyPendingRestore` 覆盖数据库文件。
多租户下「用户点恢复 = 回滚所有人的数据」显然不成立，这套模型必须重做。

**⑦ 后台任务是进程内全局单例。**
`server/src/adapters/syncScheduler.ts` 的 `jobs` 是模块级 `Map<PlatformId, ...>`，
键里不含用户——两个用户同时同步同一个平台会互相顶掉；且服务重启后续拉计划丢失。

**⑧ 前端没有登录页，也没有 401 处理。**
`client/src/api.ts` 的 `api()` 只做 `res.ok` 判断，
遇到 401 会当普通错误抛出；`client/src/App.tsx` 的路由没有守卫。

### 1.4 桌面专有部分（云端要摘掉或改写）

- `server/src/routes/update.ts` + `server/src/updater.ts`：一键自更新（下载 exe、SHA256 校验、原位替换）。
- `desktop/`（Tauri 壳）、`server/src/sea.ts`（SEA 单文件打包）、
  `server/src/widget-launcher.ts`、`server/src/instance-health.ts`。
- `/widget`（`server/src/routes/widget.ts`）：零依赖单页，**当前无任何鉴权**，
  直接暴露「当天任务 + 打卡」。云端要么下线，要么改成带一次性 token 的页面。

## 二、目标架构

### 2.1 目标形态

```
  ┌──────────────┐          ┌────────────────────────┐
  │ 浏览器界面    │──HTTPS──▶│ Caddy（TLS / 限流 / 日志）│
  └──────────────┘          └───────────┬────────────┘
                                        │ 127.0.0.1:3001
  ┌──────────────┐          ┌───────────▼────────────┐
  │ 用户脚本      │──上报───▶│ Node 进程（Express）    │
  │ (Tampermonkey│ 代理令牌  │  ① 会话中间件→req.userId │
  │  平台页面内)  │          │  ② 租户作用域路由       │
  └──────┬───────┘          │  ③ 静态托管 client/dist  │
         │                  │  ④ 后台任务（按用户）    │
         │ 同源请求          └───────────┬────────────┘
         │ （用户自己的 IP               │
         │   与登录态）       ┌───────────▼────────────┐
         ▼                   │ SQLite（WAL）+ dataDir  │
  洛谷 / 牛客 / 代码源 /       │  共享：problems/keypoints│
  LeetCode / 计蒜客 / QOJ      │  私有：user_id 表 + 配置 │
                             └────────────────────────┘

  云端直连（官方 / 社区公开 API）：Codeforces / AtCoder
```

要点：

- **两条数据入口**：浏览器界面走会话 Cookie；用户脚本走独立的代理令牌。
  **需要平台凭据的抓取只走第二条**，云端数据库里不出现任何平台 Cookie（见 2.4 / 第三节）。
- **进程数不变**：仍然是一个 Node 进程 + 一个 SQLite 文件，只是把监听地址、
  认证、租户隔离、TLS 补齐。目标量级是上千人，但这是**低频个人工具**而非高 QPS 服务，
  SQLite 单机仍够用；真正的迁移触发点是「要多实例 / 高可用」，届时再迁 Postgres。
- **前端由 Node 直接托管**：复用 `server/src/sea.ts` 里已有的
  `express.static(distDir)` + SPA fallback 逻辑，生产环境不需要 Vite。

### 2.2 多租户方案选型

| | 路线 A：单库 + 行级隔离（推荐） | 路线 B：每用户一个 SQLite 文件 |
|---|---|---|
| 做法 | 一张库，所有用户表按 `user_id` 过滤 | 每用户一个 `.db`，用 `ATTACH` 挂共享题库库 |
| 改动量 | 中（主要是把 `DEFAULT_USER_ID` 换成 `req.userId`） | 大（连接池、跨库 JOIN、迁移、配额） |
| 隔离强度 | 依赖每条 SQL 都带 `user_id`，漏一处即越权 | 物理隔离，漏查也读不到别人的数据 |
| 共享题库 | 天然共享 1.3 万题，无需重复 | 需 `ATTACH`，跨库 JOIN 要逐个核对 |
| 备份/恢复 | 需要按用户导出（新增能力） | 天然就是「一个文件 = 一个用户」，恢复模型现成 |
| 扩展性 | 好，后续可平滑迁 Postgres | 差，几百个连接/文件后难维护 |

**推荐路线 A**，理由：schema 已经按 `user_id` 建好了，改动最贴近现有代码；
共享题库在路线 B 下会变成最麻烦的部分。路线 A 的风险（漏加 `WHERE user_id`）
用测试兜住，见 Phase 2 的验收要求。

如果后续对隔离有强合规要求（例如要做付费商用、需要给用户数据做独立加密），
再评估方案 B 或迁 Postgres——本方案的分层（Phase 2 引入 `req.userId` 抽象）
会让那次迁移的成本可控。

### 2.3 认证方案

- **注册/登录**：邮箱 + 密码。密码用 `argon2id` 哈希（Node 侧可用 `@node-rs/argon2` 或
  `argon2` 原生包；若坚持零原生依赖，退而用 `node:crypto` 的 `scrypt`，强度足够且无依赖）。
- **会话**：服务端 `sessions` 表 + `httpOnly` `Secure` `SameSite=Lax` Cookie。
  相比 JWT，会话表可即时吊销（改密码、踢设备、封号），对单进程应用也更简单。
- **CSRF**：`SameSite=Lax` 覆盖大部分场景；所有写操作再加双提交 token
  （Cookie 里放随机值，请求头回带，服务端比对）。
- **限流**：登录/注册接口按 IP + 账号双维度限流，防撞库。
- **注册流程**（决策 4 = 邮箱验证）：注册 → 发验证邮件 → 点链接激活 → 才能登录。
  新增 `email_verifications(user_id, token_hash, expires_at, consumed_at)`；
  邮件走阿里云邮件推送 / 腾讯云 SES（国内发信到达率与合规性都优于自建 SMTP）。
  未验证账号的 `users.status = 'pending'`，登录时明确提示「请先验证邮箱」而不是笼统报错。
- **可选增强**：GitHub OAuth（ICPC 用户群体覆盖好）、邮箱验证码登录（免密码）。

### 2.4 抓取架构：云端不碰用户凭据

这是本方案**最重要的架构决策**，详见第三节。结论先行：

- 云端网站只直连**官方公开 API**（Codeforces、AtCoder kenkoooo）——这两个 API 本就是为程序化访问提供的。
- 需要 Cookie 的平台（洛谷 / 牛客 / 代码源 / LeetCode / 计蒜客 / QOJ）
  **由用户浏览器里的用户脚本抓取**：在平台页面内同源发起请求，
  用的是用户自己的会话与 IP，云端只接收整理后的记录，**不持有 Cookie**。
- 兜底是手动导入（已实现）。桌面版保留为本地单机模式，不再是云端抓取的主路径。

> 这条路线参考了 GoAlgo（`algo.zhiyuansofts.cn`）2026-08 的调整：
> 因洛谷官方对自动化抓取有明确管理要求，它把洛谷同步从「服务端直接抓取」
> 改成了「用户本人在浏览器中主动同步」。

## 三、抓取与风控策略

### 3.1 风控到底在防什么

平台的风控不是笼统的「防爬虫」，它对不同信号的敏感度差别很大：

| 信号 | 敏感度 | 说明 |
|---|---|---|
| **一个 IP 访问多个账号** | **极高** | 账号农场 / 撞库 / 代刷的典型特征。云端集中 N 个用户的 Cookie 就是这个模式 |
| 请求节奏机械（固定间隔、无抖动） | 高 | 正常人有停顿和随机性 |
| 全量历史回填 | 高 | 一次性拉几千条提交，是最像爬虫的行为 |
| 数据中心 IP 段 | 中–高 | 阿里云 / 腾讯云 IP 段在平台黑名单里是公开信息；但**国内平台对国内机房 IP 的容忍度显著高于境外 IP** |
| UA / 请求头与浏览器不一致 | 中 | 项目已有 `ua.<platform>` 设置项处理 |
| 短时间高频 | 中 | `server/src/net/hostThrottle.ts` 已在处理 |

**关键结论：「一个出口 IP 访问多个账号」是集中式云端抓取无法绕开的结构性问题。**
其余信号都可以缓解，只有这一条，缓解不了——因为它就是集中式的定义。

按决策 1（上千人），哪怕只有 20% 的用户用洛谷，也是**两百个账号从同一个 IP 出去**，
这不是「调参数能不能躲过去」的问题。

### 3.2 可选方案（按推荐度排序）

#### 方案 1 · 抓取下沉到用户侧：浏览器用户脚本（推荐，主路径）

云端只做存储 / 分析 / AI，抓取由**用户浏览器里的用户脚本**（Tampermonkey）完成。
参考 GoAlgo 的做法：脚本只在已登录的平台页面内读取用户本人的提交记录，
整理后同步到云端，**不读取、不保存、不上传平台密码与 Cookie**。

> 这不只是「躲风控」的技术选择。洛谷官方对自动化抓取有明确的管理要求，
> 服务端抓取除了技术风险，还有**平台规则合规风险**。用户脚本从根上回避了这个问题。

**为什么用户脚本优于桌面代理**

| | 浏览器用户脚本 | 桌面代理 |
|---|---|---|
| 安装门槛 | 装 Tampermonkey + 点一次安装 | 下载 + 安装 + 可能的 SmartScreen / 签名警告 |
| 会话来源 | 直接用浏览器现有登录态，**零凭据外流** | 需从浏览器取 Cookie 或独立登录 |
| 请求特征 | **同源、同 IP、同 UA / TLS 指纹**，与站点自身 XHR 无异 | 独立进程，指纹与浏览器不同 |
| 后台能力 | 仅页面打开时（可设定时器） | 可后台常驻 |
| 分发成本 | 一个 `.user.js` 文件 + 自动更新 | 多平台打包、代码签名、公证 |
| 平台改版 | 更新脚本（Tampermonkey 自动更新） | 需发新版客户端 |

同源这一条是关键：脚本发出的请求与洛谷页面自己的 XHR 在服务端看来完全一致，
既不是新的 IP，也不是新的指纹，连请求头顺序都一样。

结论：**用户脚本作为主路径**；桌面代理降级为「不想开浏览器页面时的备选」，排到 Phase 8。

**关键设计点**

1. **薄脚本，厚服务端**：脚本只做「用用户会话取原始数据 + 上报」，
   解析 / 归一化 / 去重全部留在服务端，复用 `server/src/adapters/` 的现有代码。
   脚本越薄，平台改版时需要更新的越少——这是脚本能否长期存活的关键。
2. **增量早停**：脚本先问服务端「这个平台我已知的最新提交号」，
   在平台上翻页到命中已知 id 就停（沿用适配器已有的 `knownExternalIds` 早停逻辑）。
   避免每次全量拉取——全量回填是最像爬虫的行为。
3. **上报通道**：用 `GM_xmlhttpRequest`（绕过 CORS 与页面 CSP），
   元数据里声明 `@connect <我们的域名>`，不依赖平台页面是否允许跨域。
4. **连接与授权**：用户在平台页面点「连接」→ 打开我们的授权页（用户在云端已登录）→
   确认账号与风险提示 → 服务端签发**代理令牌**（长期有效、可吊销、
   只能上报自己的数据、读不到任何其他内容）→ 经 `window.postMessage` 回传脚本，
   用 `GM_setValue` 保存。全程不接触平台密码与 Cookie。
5. **定时同步**：面板可选 1–12 小时间隔或关闭（GoAlgo 同款），默认建议 6–12 小时；
   服务端按 `userId` 限流兜底，防止有人把间隔调到 1 分钟把大家拖下水。
6. **版本治理**：`GET /api/agent/userscript/latest` 返回最新版本；
   服务端拒绝过旧版本并回「请更新脚本」；`.user.js` 带
   `@updateURL` / `@downloadURL`，Tampermonkey 自动更新。

**平台覆盖**：洛谷 / 牛客 / 代码源 / LeetCode / 计蒜客 / QOJ 都可在其页面内同源取数。
QOJ 有 Cloudflare 挑战，但用户既然能打开页面，挑战就已通过，同源请求可直接复用会话。

**附带收益**（对上千人规模尤其关键）

- **云端不再托管任何平台 Cookie**：密钥托管责任、法律风险、泄露爆炸半径一并消失。
  这条的价值可能比风控本身还大。
- 出站流量不占服务器带宽，国内机房访问境外平台的跨境链路问题也不再影响抓取。
- 上千人的抓取负载分散到用户浏览器，服务器成本大幅下降。

**代价与注意**

- 用户要装 Tampermonkey；移动端浏览器基本不支持（手机用户走手动导入）。
- **脚本供应链安全**：脚本运行在平台页面上，若被篡改可读取页面内容。
  对策：源码在仓库里公开、零第三方依赖、只从自己的 HTTPS 域名分发、
  脚本内不引入任何远程代码。
- **数据可信度**：客户端上报理论上可伪造。当前是自用工具，可接受；
  将来若做排行榜 / 社交功能需重新设计信任模型。

#### 方案 2 · 云端只抓无需凭据的公开数据（推荐，与方案 1 并行）

| 平台 | 云端直连可行性 |
|---|---|
| Codeforces | ✅ 官方公开 API，本就是为程序化访问提供的（国内机房跨境链路需实测） |
| AtCoder | ✅ kenkoooo 社区 API，同为公开 API |
| 牛客 | ⚠️ 公开 HTML、无需凭据，但本质仍是页面抓取；按洛谷的先例，建议也走用户脚本 |
| 洛谷 / 代码源 / LeetCode / 计蒜客 / QOJ | ❌ 需要 Cookie，走方案 1 |

对用户的承诺是：**不装任何东西也能用 CF / AtCoder；要同步洛谷等平台，装一次脚本即可。**

> 边界要划清楚：CF / AtCoder 用的是**官方或社区公开 API**，属于正常集成；
> 其余平台是**页面抓取**，即便技术上不需要凭据（牛客），也不应默认由服务端代劳。

#### 方案 3 · 住宅代理 / 代理池（不推荐作为主方案）

- 能解决「IP 段被标记」，但解决不了「一个出口访问多个账号」——
  除非给**每个用户分配独立出口**，那就是按人计费的住宅代理。
  住宅代理普遍按流量计费，上千人规模成本极高。
- 国内住宅代理供应商合规性参差，有法律风险。
- 结论：可留作少数「必须云端同步」用户的付费选项，不做主路径。

#### 方案 4 · 强化节流与行为拟真（必要，但只能缓解）

无论走哪条路都要做，云端直连 CF / AtCoder 时尤其重要：

- **限流维度从域名改为「账号 + 域名」**：现在 `server/src/net/hostThrottle.ts` 只按域名节流，
  多用户并发会互相挤兑同一个域名配额；需按 `userId:platform` 独立限流。
- **加抖动**：间隔带随机量（如 40s ± 30%），去掉机械节奏。
- **错峰**：用户触发后随机延迟 0–N 分钟再实际执行，避免整点批量。
- **默认只做增量**：不提供「一键全量回填」；历史补全只走本地代理。
- **快速退避**：遇到 403 / 429 / 风控页立即停止该账号并标记，
  不做重试轰炸（`syncScheduler` 已有「鉴权失败立即停止」的逻辑，沿用即可）。
- **单账号并发恒为 1**，全局出站并发设硬上限。

#### 方案 5 · 官方渠道优先 + 手动导入兜底

- CF 官方 API 已是正路；洛谷 / 牛客等是否有开放平台或数据导出值得调研，有则优先。
- 手动导入（`server/src/routes/import.ts` 已实现）永远是兜底。

### 3.3 落地建议

- **主路径**：方案 1 + 方案 2。云端不碰任何平台 Cookie；
  **浏览器用户脚本**作同步代理；CF / AtCoder 走云端直连。
- **兜底**：方案 4 的节流与退避，配合方案 5 的手动导入。
- **明确不做**：方案 3 的代理池，除非将来出现明确的付费需求。

> 这条路线顺带**大幅缩小了 Phase 3 的范围**：云端不再存平台 Cookie，
> 只需保护 AI API Key（BYOK），加密改造与合规风险都显著下降。

> 也顺带简化了 Phase 4：用户脚本是一个纯前端产物（一个 `.user.js` 文件），
> 不需要打包、签名、公证，也不占用户磁盘——比发布桌面客户端轻得多。

## 四、分阶段实施计划

每个阶段结束后服务都应处于「可运行、可回滚」状态。

### Phase 0 · 决策结论（已完成）

已确认，见第六节。对后续计划的直接影响：

- **上千人** → 数据访问层必须做抽象（Phase 2 的 `settings/store.ts` 是起点），
  为 Postgres 迁移留门；但 SQLite 单机本身在千人规模仍够用（这是低频个人工具，不是高 QPS 服务）。
  **真正的迁移触发点是「要多实例 / 高可用」，不是用户数本身。**
- **国内部署** → 域名 ICP 备案是硬前置（备案周期 2–4 周，应**立刻启动**，否则会卡住上线）；
  邮件服务用阿里云邮件推送 / 腾讯云 SES；CF / AtCoder 的跨境链路需实测。
- **BYOK + 预留平台代付** → AI Key 解析要做成可切换的解析层，不能把「用户自己的 Key」写死在调用点。
- **邮箱验证** → 注册流程与邮件服务纳入 Phase 1。
- **桌面并存** → 桌面版升格为同步代理，见第三节方案 1，独立成 Phase 4。

### Phase 1 · 认证地基与请求上下文（3–4 天）

**目标**：服务能识别「当前是谁」，未登录一律 401。

**任务**

1. `server/src/db/schema.sql` 新增两张表、给 `users` 补列：
   - `users` 补 `email`、`password_hash`、`status`。**注意 SQLite 的 `ALTER TABLE ADD COLUMN`
     不支持 `UNIQUE` 约束**，所以老库迁移要写成
     `ALTER TABLE users ADD COLUMN email TEXT` + 单独 `CREATE UNIQUE INDEX ... ON users(email)`
     （NULL 在 SQLite 唯一索引里互不冲突，正好允许「历史用户暂无邮箱」）；
     `status` 需带 `NOT NULL DEFAULT 'active'`。迁移必须幂等，
     `server/src/db/index.ts` 的 `migrate()` 已有按 `PRAGMA table_info` 补列的范式，照抄即可。
   - `sessions(id TEXT PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users(id), created_at, expires_at, user_agent, ip)`。
   - `user_settings(user_id INTEGER NOT NULL REFERENCES users(id), key TEXT NOT NULL, value TEXT NOT NULL, PRIMARY KEY(user_id, key))`——先建表，Phase 2 再切流量。
   - `email_verifications(id INTEGER PRIMARY KEY, user_id, token_hash, expires_at, consumed_at)`
     与 `password_resets(...)`（同构）：存 **token 的哈希**而非原文，
     一次性消费（`consumed_at` 非空即失效），有效期 24 小时。
2. 新增 `server/src/auth/`：`password.ts`（哈希/校验）、`session.ts`（签发/校验/吊销）、
   `email.ts`（发信封装，开发环境打日志、生产走阿里云邮件推送 / 腾讯云 SES）、
   `routes.ts`：
   - `POST /api/auth/register`（建 `status='pending'` 账号并发验证邮件，**不直接给会话**）
   - `POST /api/auth/verify`（消费 token → `status='active'`）
   - `POST /api/auth/resend-verification`
   - `POST /api/auth/login` / `POST /api/auth/logout` / `GET /api/auth/me`
   - `POST /api/auth/password-reset/request` / `POST /api/auth/password-reset/confirm`
3. 新增 `server/src/auth/middleware.ts`：解析会话 Cookie → 挂 `req.userId`；
   白名单放行 `/api/auth/*`、`/api/health`、静态资源。
   已登录但 `status='pending'` 的账号访问业务接口返回 403 + 明确错误码，前端引导去验证页。
4. `server/src/index.ts`：`app.use(authMiddleware)` 注册在所有 `/api` 路由**之前**；
   `app.listen` 地址改为 `process.env.HOST ?? '127.0.0.1'`（默认仍是回环，公网由反代接入）。
5. 删除 `server/src/constants.ts` 的 `DEFAULT_USER_ID` 导出前，先加一个临时桥接：
   `req.userId` 未注入时回退 1，保证 Phase 1 结束时其余代码仍能跑。

**涉及文件**：`server/src/db/schema.sql`、`server/src/db/index.ts`、`server/src/index.ts`、
新增 `server/src/auth/*`、`server/test/auth.test.ts`

**验收**

- 未带 Cookie 访问任意 `/api/*`（除白名单）返回 401，且响应体是 JSON 不是 HTML。
- 注册后账号为 `pending`：未验证前不能登录业务接口；点验证链接后变 `active` 可正常使用。
- 验证 token 用过即失效、过期即失效；重复注册同一邮箱有明确提示且不泄露「该邮箱是否已注册」之外的信息。
- 登录 → `GET /api/auth/me` 返回正确用户；登出后旧 Cookie 立即失效。
- 会话过期后访问返回 401。
- 忘记密码全流程可用（请求 → 收信 → 重置 → 用新密码登录）。
- `npm run typecheck -w server` 与 `npm test -w server` 全绿。

### Phase 2 · 租户隔离：配置表拆分 + 全量查询加用户维度（5–7 天）

**任务**

   只依赖解析结果，**不得直接读 `ai.apiKey`**。这样将来切平台代付只改解析层，
   顺带为配额与计费留出挂钩点（`ai_usage(user_id, model, prompt_tokens, completion_tokens, at)` 表可同期建好）。

**涉及文件**：`server/src/settings/store.ts`（新）、`server/src/config.ts`、
`server/src/routes/settings.ts`、`server/src/adapters/{sync,syncScheduler}.ts`、
`server/src/plans/planService.ts`、`server/src/ai/templateContext.ts`、
`server/src/ai/keyResolver.ts`（新）、
其余 12 个 `server/src/routes/*.ts`、`server/src/constants.ts`（最终删除）

### Phase 3 · 秘密加密与安全加固（2–3 天）

**目标**：数据库文件泄露不等于凭据泄露。

**任务**

1. 新增 `server/src/security/secretBox.ts`：AES-256-GCM 信封加密，
   主密钥来自环境变量 `ICPC_SECRET_KEY`（32 字节，缺失时启动即失败并给出生成命令）。
   格式 `v1:<iv>:<tag>:<ciphertext>`，带版本号便于轮换。
2. 落库前加密、读取时解密，作用范围：`ai.apiKey`、`ai.searchApiKey`、
   `cookie.<platform>`、`csrf.<platform>`。写入 `user_settings` 的密文，
   `settings.ts` 回显逻辑保持不变（继续只回打码值）。
   **云端模式下 Cookie 相关接口直接关闭**（见第三节方案 1：云端不持有平台凭据），
   但加密逻辑仍保留——桌面版在本地存 Cookie，同样受益；且将来若开放
   「云端代管」也是现成的。
3. 老库迁移：识别明文值 → 加密后原地覆盖（幂等，靠 `v1:` 前缀判断）。
4. 反代层与进程层加固：
   - 生产环境强制 `NODE_ENV=production`，`securityHeaders` 补 `Strict-Transport-Security`、
     收紧 `Content-Security-Policy`（Ant Design 需要 `style-src 'unsafe-inline'`，如实配置）。
   - `express.json` 限额保持 `2mb`；上传类接口（AI 附件、导入）单独设限。
   - 新增 `server/src/security/rateLimit.ts`：登录、注册、同步触发、AI 对话四类接口限流。
5. 审计日志：登录成功/失败、改密、Cookie 变更、导出数据，追加写 `dataDir/audit.jsonl`。

**验收**

- 用 `sqlite3` 直接打开库文件，`grep` 不到任何明文 Key / Cookie。
- 缺少 `ICPC_SECRET_KEY` 时进程启动失败并打印可操作的提示。
- 连续错误登录触发限流；正常用户不受影响。

### Phase 4 · 浏览器同步代理：用户脚本 + 云端接收（5–7 天）

**目标**：把第三节的结论落地——云端不持有平台 Cookie，
需要凭据的抓取改由用户浏览器里的用户脚本完成。

**接口契约**：见 `docs/2026-09-19-phase4-同步代理接口文档.md`
（`/api/agent/*` 的请求响应形状、授权握手时序、脚本侧取数清单、服务端改造点）。

**任务**

1. **云端新增代理接口**（新增 `server/src/routes/agent.ts`）：
   - `POST /api/agent/authorize`：用户在云端已登录，确认风险提示后签发**代理令牌**
     （长期有效、可吊销、只能上报自己的数据）。令牌存哈希，不存原文。
   - `GET /api/agent/sync/context?platform=luogu`：返回该用户在该平台的
     已知最新提交号 / 游标，供脚本做增量早停。
   - `POST /api/agent/sync/ingest`：接收脚本上报的原始记录，
     交给 `server/src/adapters/` 现有的解析与归一化逻辑处理。
     `submissions` 已有 `UNIQUE(user_id, platform, external_id)`，天然幂等。
   - `GET /api/agent/userscript/latest`：版本检查。
   全部用代理令牌鉴权（`Authorization: Bearer <agent-token>`），不复用会话 Cookie。
2. **用户脚本**（新增 `agent/userscript/`，TS 源码 + 构建成 `.user.js`）：
   - 元数据：`@match` 各平台域名、`@grant GM_xmlhttpRequest / GM_setValue / GM_getValue`、
     `@connect <我们的域名>`、`@updateURL` / `@downloadURL`。
   - 悬浮面板：连接状态、手动同步、1–12 小时间隔或关闭、进度显示、错误提示。
   - 取数逻辑按平台分模块，但**只负责取原始数据**，不做解析。
   - **零第三方依赖**，脚本内不引入任何远程代码（供应链安全，见第三节）。
   - **v1 覆盖 5 个平台**：洛谷 / 牛客 / 代码源 / LeetCode / 计蒜客。
     **QOJ 不进 v1**（浏览器内是否仍需 HTTP/1.1 未经实测），用户走手动导入。
   - 计蒜客练习段默认开但降频：定时同步时服务端关闭该段，只在手动同步时跑；
     段内间隔 2000ms、预算 100 条 / 10 页（比赛段 1500ms / 300 条 / 30 页）。
3. **令牌按浏览器粒度**：`(user_id, client_id)` 唯一，同一浏览器重连即换发并作废旧令牌；
   设置页按浏览器列出、可单独吊销。为桌面版预留 `clientKind=desktop` 与协议复用点。
4. **云端关闭 Cookie 平台直连**：`POST /api/sync/:platform` 在云端模式下只放行
   codeforces / atcoder；洛谷 / 牛客 / 代码源 / LeetCode / 计蒜客 / QOJ
   返回明确的「请安装同步脚本」错误码，前端据此显示引导而不是抛异常。
5. **节流维度改造**（第三节方案 4）：`server/src/net/hostThrottle.ts` 从纯域名级
   改为「`userId:platform` 级 + 域名级」双层；同步间隔加抖动；单账号并发恒为 1。
6. **前端引导**：设置页「平台账号」区增加「安装同步脚本」入口与图文步骤；
   授权页 `client/src/pages/AgentAuthorize.tsx` 展示账号信息与风险提示
   （间隔越短风控风险越高、请确认登录的是已绑定的账号）。
7. **兜底**：不想装脚本的用户仍可用手动导入（已实现）+ CF/AtCoder 云端直连。

**涉及文件**：新增 `server/src/routes/agent.ts`、`agent/userscript/*`、
新增 `client/src/pages/AgentAuthorize.tsx`、`server/src/routes/sync.ts`、
`server/src/net/hostThrottle.ts`、`server/src/import/*`、
新增 `server/test/agent-ingest.test.ts`

**验收**

- 云端模式下 `/api/sync/luogu` 返回引导性错误码，且服务端**不存在任何接受平台 Cookie 的路径**。
- 完整走通：装脚本 → 平台页面点连接 → 云端授权 → 点同步 → 数据入库。
- 脚本上报后云端正确去重入库，重复上报幂等；增量早停生效（第二次同步不翻页到底）。
- 代理令牌吊销后上报立即 401；令牌只能写入自己 `user_id` 的数据。
- 同一浏览器重连不新增令牌行；吊销其中一个浏览器不影响其他浏览器。
- 计蒜客定时同步不跑练习段；手动同步跑，且两段预算互不挤占。
- 服务端拒绝过旧脚本版本并提示更新。
- 两个用户同时同步同一平台互不影响（限流键含 userId）。

   - `desktop/`、`sea.ts`、`widget-launcher.ts` 保留在仓库（本地版继续用），
     但不进入云端镜像。
6. `server/config.example.json` 增补云端字段（`host`、`publicUrl`、`allowRegister`、`sessionTtlDays`）。
7. **国内部署专项**（对应决策 2）：
   - ICP 备案 + 域名解析 + 公安联网备案；备案主体与隐私政策、用户协议一起准备。
   - 服务器选型：阿里云 / 腾讯云轻量应用服务器起步，`data` 卷单独挂载（便于快照与扩容）。
   - **实测跨境链路**：从目标机房访问 `codeforces.com` / `kenkoooo.com` 的延迟与成功率；
     若不达标，把 CF / AtCoder 也划给用户脚本（Phase 4 的协议已支持，无需改动）。
   - 邮件服务接入阿里云邮件推送 / 腾讯云 SES，配好 SPF / DKIM / DMARC。
   - 合规：用户数据的收集范围、存储期限、删除方式要写进隐私政策——
     BYOK 模式下云端只存 AI Key，这是相对好交代的一点。

**验收**

- `docker compose up -d` 后，`https://<域名>` 能打开登录页。
- 容器重启后数据仍在（卷挂载正确）。
- 健康检查失败时容器能被自动重启。
- 镜像里不含 `desktop/` 产物与 `server/release/`。
- 从目标国内机房实测 CF / AtCoder 接口连通性并记录数据，据此决定是否改走用户脚本。
- 验证邮件能送达主流邮箱（含 QQ / 163 / Gmail），且不落垃圾箱。

### Phase 6 · 备份 / 后台任务 / 运维（3–4 天）

**目标**：云端可长期无人值守运行。

**任务**

1. **备份模型重做**：`server/src/backup.ts` 的整库 `VACUUM INTO` 保留为**实例级**兜底，
   另加**用户级**导出/恢复：按 `user_id` 导出 JSON（或按用户 `ATTACH` 出一份小库）。
   设置页「备份与恢复点」的语义随之改为「导出/导入我的数据」。
2. **恢复不再需要重启**：用户级恢复 = 事务内 delete + insert，无需 `restore-pending.json`。
3. **后台任务**：Phase 2 已按用户分键；本阶段补
   - 进程重启后从 `platform_accounts.backfill_page` 自动续拉（当前需用户再点一次同步）；
   - 全局并发上限，防止 N 个用户同时触发同步把出站打满。
4. **可观测性**：结构化日志（JSON 行）、关键指标（请求量/错误率/同步成败/AI token 消耗）、
   `/api/admin/*` 只读接口（用户列表、同步失败排行、磁盘占用），管理员由环境变量白名单指定。
5. **配额**：单用户提交数上限、题库拉取频率上限、AI 对话每日次数上限（若走平台 Key）。

**验收**

- 用户 A 的恢复操作不影响用户 B。
- 杀掉进程重启后，被截断的同步能自动续上。
- 管理员能看到「谁在什么时候同步失败、错误码是什么」。

### Phase 7 · 前端登录体验（2–3 天）

**目标**：登录/注册/登出/会话过期，体验完整。

**任务**

1. 新增 `client/src/pages/Login.tsx`（登录 + 注册切换，Ant Design `Form`）
   与 `client/src/pages/VerifyEmail.tsx`（注册后提示查收邮件 / 点链接激活 / 重发）；
   忘记密码走 `client/src/pages/ResetPassword.tsx`（请求 → 收信 → 重置）。
2. `client/src/App.tsx`：未登录时渲染登录页，登录后渲染现有布局；
   新增 `/login`、`/verify`、`/reset` 路由与 `/logout` 动作；
   `status='pending'` 的账号登录后落到 `/verify` 而不是主界面。
3. `client/src/api.ts`：`api()` 遇到 401 → 清会话状态并跳转登录页
   （保留原路径，登录后回跳）；网络错误与业务错误区分提示。
4. 用户菜单：侧边栏底部展示当前用户 + 登出；设置页加「账号与安全」（改密码、退出所有设备）。
5. **本地状态归属**：`Assistant.tsx` 的 AI 会话记录、`menuConfig.tsx` 的菜单顺序、
   `editorSettings.ts` 的缩进偏好目前都在 `localStorage`。
   - 缩进/菜单顺序：保持本地即可（浏览器偏好）。
   - **AI 会话记录：建议迁到服务端**（新增 `ai_sessions` / `ai_messages` 表），
     否则换设备/换浏览器就丢，与「云端网站」的预期不符。这一步可作为独立任务排在最后。

**验收**

- 未登录访问任意页面 → 跳登录页；登录后回到原页面。
- 会话过期时页面不白屏，给出提示并跳登录。
- 移动端（窄屏）登录页与主布局可用。

### Phase 8 · 后续演进（按需，不在本次范围）

- **桌面代理**：为「不想开着浏览器页面」的用户提供后台同步。
  复用 `desktop/`（Tauri 壳 + Node 核心），走同一套代理令牌与 `/api/agent/*` 协议，
  只是把取数从浏览器挪回 Node。用户脚本先行，桌面代理后补，避免一开始就背两套实现。
- **迁 Postgres**：当并发写入或用户量超过单进程 SQLite 舒适区时。
  建议先做数据访问层抽象（Phase 2 的 `settings/store.ts` 是第一步），再整体替换。
- **多实例水平扩展**：需要把会话、后台任务调度、限流计数外置（Redis），
  并把 SQLite 换成 Postgres。
- **AI 平台代付**：若决定由平台提供 AI Key（而非 BYOK），需要配额、计费、
  按用户 token 计量与滥用防护。

## 五、风险清单

| 风险 | 说明 | 应对 |
|---|---|---|
| **跨租户数据泄漏** | 路线 A 依赖每条 SQL 带 `user_id`，漏一处就是事故 | Phase 2 的静态审计脚本 + 隔离测试；代码评审时把「新查询是否带 user_id」列为必查项 |
| **平台风控 / 封号** | 集中式抓取时「一个出口 IP 访问多个账号」无法缓解，上千人规模下必然触发 | **已由架构消解**：凭据平台改由浏览器用户脚本抓取（第三节方案 1），云端不碰 Cookie；残余风险在云端直连的 CF / AtCoder，用方案 4 的节流兜底 |
| **平台规则合规** | 洛谷等平台对自动化抓取有明确管理要求，服务端抓取可能违反其规则 | 同上一行——用户脚本在用户自己的会话内取自己的数据，从根上回避 |
| **脚本安装门槛** | 方案 1 的前提是用户愿意装 Tampermonkey；不愿装的人只能手动导入或只用 CF/AtCoder | 把「不装也能用」做好（CF/AtCoder 直连开箱即用）；首次同步洛谷时给出图文引导而不是报错 |
| **脚本供应链安全** | 脚本运行在平台页面上，一旦被篡改可读取用户的页面内容 | 源码在仓库公开、零第三方依赖、只从自己的 HTTPS 域名分发、脚本内不引入远程代码；令牌只能写自己的数据 |
| **脚本随平台改版失效** | 平台改版会打断脚本，用户会以为是我们的 bug | 薄脚本设计（解析在服务端）+ `@updateURL` 自动更新 + 服务端拒绝过旧版本并提示「请更新脚本」 |
| **上报数据可信度** | 客户端上报理论上可伪造 | 当前是自用工具，可接受；若将来做排行榜 / 社交需重新设计信任模型，先记在案 |
| **ICP 备案周期** | 国内部署必须先备案，2–4 周且不可压缩，会成为上线阻塞点 | Phase 1 开工同时启动备案；开发期用境外测试机或本地环境，不阻塞编码 |
| **跨境链路不稳** | 国内机房访问 Codeforces / AtCoder 可能超时或抖动 | Phase 5 实测；必要时把 CF / AtCoder 同步也交给用户脚本（协议已支持） |
| **邮件送达率** | 验证邮件进垃圾箱会导致注册转化失败 | 用阿里云邮件推送 / 腾讯云 SES 而非自建 SMTP；配好 SPF / DKIM / DMARC；提供「重发」与备用验证路径 |
| **密钥托管责任** | 云端仍持有用户的 AI API Key（BYOK） | Phase 3 加密存储 + 最小权限 + 审计日志；隐私政策写明存储范围与删除方式。平台 Cookie 已不落云端，风险面显著缩小 |
| **同步 API 阻塞事件循环** | `node:sqlite` 是同步 API，AI 流式输出期间的数据库调用会阻塞其他请求 | 第一版可接受；出现卡顿时把重查询改为缓存或迁 Postgres |
| **备份模型迁移** | 老用户的「一键恢复」语义变化，可能造成误操作 | UI 文案明确区分「恢复我的数据」与「实例快照」；迁移期保留只读的旧备份下载 |
| **成本失控** | 上千人规模下，AI token 与带宽是主要成本 | 当前 BYOK 已把 AI 成本外置；Phase 2 建 `ai_usage` 表，切平台代付时即可做配额与告警 |

## 六、决策结论（已确认）

| # | 问题 | 结论 | 对方案的影响 |
|---|---|---|---|
| 1 | 目标用户量级 | **上千人** | 数据访问层必须抽象（`settings/store.ts` 起步），为 Postgres 留门；SQLite 单机在千人规模仍够用，迁移触发点是「多实例 / 高可用」而非用户数 |
| 2 | 部署位置 | **国内服务器** | ICP 备案是硬前置（2–4 周，**建议立刻启动**）；邮件走阿里云 / 腾讯云；CF / AtCoder 跨境链路需实测 |
| 3 | AI Key 谁出 | **当前 BYOK，预留平台代付** | 新增 `server/src/ai/keyResolver.ts` 收敛 Key 解析；同期建 `ai_usage` 表为配额计费留位 |
| 4 | 注册方式 | **邮箱验证** | Phase 1 纳入注册验证 + 忘记密码全流程 |
| 5 | 桌面版去留 | **云端与桌面版并存** | 云端与本地版长期并存；抓取侧以**浏览器用户脚本**为主（第三节方案 1），桌面代理作为后续备选排入 Phase 8 |

**由此确定的抓取路线**：云端直连 CF / AtCoder（官方 / 社区公开 API）；
洛谷 / 牛客 / 代码源 / LeetCode / 计蒜客 由**用户浏览器里的用户脚本**抓取上报，
云端不持有平台 Cookie。QOJ 不进 v1（浏览器内是否仍需 HTTP/1.1 未经实测），走手动导入。

## 七、整体验收标准

- 公网 HTTPS 可访问，注册 → 邮箱验证 → 登录 → 使用全流程通畅。
- 两个用户的数据（提交、计划、模板、题单、设置、凭据）互相完全不可见。
- **云端数据库中不存在任何平台 Cookie**；AI Key 落库为密文。
- 云端直连只走 CF / AtCoder；洛谷等平台由**浏览器用户脚本**上报且幂等。
- 用户脚本完整走通「安装 → 连接授权 → 同步 → 入库」，且服务端没有任何接受平台 Cookie 的路径。
- 用户级备份/恢复可用，且不影响其他用户。
- 服务重启后数据不丢、被截断的同步能续上。
- `npm run typecheck`、`npm test`、`npm run lint:tenant` 全绿。
