## 2. 平台数据获取

### 2.1 牛客：难度分校验器把真实值判成未知（**本轮已修**）
- 证据：`shared/src/difficulty.ts` 的 `parseNowcoderScore` 旧规则要求 `n % 100 === 0`，
  注释依据是「题库列表页 300 行样本恒为整百分值」。逐题实测**搜索结果页**（老题）给出非整百分值，
  且确实位于难度列：`NC16640=1049`、`NC22014=623`、`NC22158=726`、`NC22231=876`、`NC24739=972`
  （同行通过人数列分别为 5593 / 24207 / 23365 / 7486 / 1597，均不等于该值）。
  库内还留有 9 行历史非整百分值（旧版本接受过）→ 断言被证伪，是后来收紧时引入的回归。
- 修法：校验器只做值域校验（200–4000 整数）；「防读到通过数列」改由
  `parseNcRowCells` 的**列结构校验**负责（题目锚点 + 难度单元格 + 操作锚点 `js-collect-question`
  恒为最后一格，且难度文本 ≠ 通过人数文本）。
- 实测收益：`server/data/icpc.db` 牛客 41 道缺难度题里 **7 道被补上**（319680/319682/319684 = 700/700/800，
  323650~323656 = 400/600/900/900 的原生分），另 30 道站上难度单元格本身为空、4 道题目已不存在。

## 3. QOJ 难度：ICPC/CCPC 公开榜单（**本轮新增**，`server/src/analysis/icpcBoard.ts`）

1. `xcpcrating` 数据集的 `problem-catalog.json`：`canonicalId: "qoj:<id>"` → 赛场键 + 题号字母
   （如 `qoj:20016` → `icpc/icpc2026/icpc2026preliminary-1:A`）；
   `problem-types/2023-present-all-qoj-v2.json` 另给逐题 `detailTags`（知识点标签）。
   **GitHub 直连在本机被 hosts 屏蔽** → 走 `cdn.jsdelivr.net` 镜像，ghproxy 兜底（均实测 200）。
2. RankLand 公开 API：`/api/v2/public/contests`（赛场索引）→ `/api/v2/public/files/{id}` →

## 7. 第二轮：把「逐题查询」改成「整表扫描」，并修正过时难度值（2026-09-27 追加）

### 7.1 起因：defer 的代价被低估了

§5 曾把「牛客/代码源仅缺原生值的行」作为**已知代价**：逐题平台每补一行要打一次上游，
默认 defer 是刻意的取舍。但实测库内数据后发现这个取舍有**两个副作用**（不是省几个请求的问题）：

| 平台 | 缺原生值的行 | 整表可覆盖 | 其中难度与上游**不一致**（过时值） |
|---|---|---|---|
| 牛客 | 1082 | 1055（97.5%） | **280** |
| 代码源 | 459 | 459（100%） | **411**（89%） |
| 洛谷 | 2418 | 63（2.6%） | 63 |

即：**defer 让 691 行「错误难度值」永远不会被修正**（代码源 459 行里 411 行的难度是错的），
而不只是「原生原文列空着」。原因是 `pickBackfillTargets` 只在 `difficulty IS NULL / native_difficulty IS NULL /
tags='[]'` 时入选 —— 难度有旧值但原生值为空的行一旦被 defer，就再也没机会被上游值改写。

### 7.2 改法：复用已有题库拉取器做整表扫描（参考项目同款做法）

`adapters/problemBank.ts` 的 `fetchNowcoderBank` / `fetchDaimayuanBank` 本来就是「分页列表一次拿全」，
之前只被「拉取题库」用，回填链路却逐题查。本轮把两者接到回填的整表通道（`TABLE_FETCHERS`）：

- 新增 `BankFetchOptions.wantKeys`：目标题号全部命中即停止翻页（`makeWantedTracker`）。
  库内常常只有几道待补题，不必为此扫完整表。
- `fetchNowcoderTable` / `fetchDaimayuanTable`：拉表 → `bankToTable` → 内存查；`fetchProblemMeta` 的
  nowcoder/daimayuan 分支改走整表，删掉 `fetchDaimayuanMeta`（逐题 JSON）。
- `PER_PROBLEM_NATIVE_DEFERRED` 从 `{luogu, nowcoder, daimayuan}` 收窄到 `{luogu}`；
  `PLATFORM_LIMITS` 中牛客/代码源改为整表类（`delayMs: 0, failLimit: null, maxPerRun: 20000`）。
- `repaired` 现在也覆盖「过时难度值被修正」，明细带 `修正难度 700→800`（前端文案同步为「修标题/标签/难度值」）。

洛谷**不动**：实测整表接口对本库覆盖率仅 63/2418（本库的洛谷题多来自提交记录，不在题库列表前若干页），
且要扫 77 页/140s，收益不抵成本；仍保持逐题 + 默认 defer（这点已写进 README「已知限制」）。

### 7.3 关键回归风险与实测排除

改整表最大的风险是**丢掉原来逐题路径能补上的难度**。实测逐项排除：

- 原本靠逐题搜索结果页补上的 **7 道牛客「真缺难度」题**（319680 / 319682 / 319684、323650~323656）
  **全在整表结果内**，且给出原生分 700/700/800/400/600/900/900 → 改用整表**不丢**这 7 行。
- 整表未覆盖的 19 道牛客缺难度题：逐题兜底实测对其中 15 道只拿到「难度列为空」、4 道题目不存在
  → **逐题兜底对难度毫无增益**，故不保留兜底（否则每轮又制造几十次无效请求，与 §0「无效请求 0 次」的目标冲突）。
- `deriveIdentityNative`（零请求本地推导牛客原生值）与整表**不冲突**：实测它会命中的 689 行里
  **0 行**与上游不一致（过时的 280 行全部落在钳位区间之外、推导函数本就返回 null 跳过），
  两者互补：推导吃掉 689 行零请求，整表补剩下的 366 行并修正 280 行。

### 7.4 附带修掉的性能坑：逐行自动提交

整表化之后单轮写库量从「每平台 ≤2000」涨到「上万行」，暴露出 `backfillPlatform` 一直是
**逐行自动提交**（node:sqlite 默认 autocommit → 每条 UPDATE 一个事务、一次 fsync）。
实测一次 1.9 万目标的回填里写库占约 70s。改为**分批提交**（`WRITE_BATCH = 100`，
批次满即 COMMIT、循环结束收尾 COMMIT、异常 ROLLBACK）：

- 为什么不是「整平台一个事务」：洛谷在循环里发真实网络请求，一个长事务横跨 290 次网络往返
  会长时间占住写锁并让 WAL 膨胀；分批同时把「异常回滚」的粒度限制在一批内（保住已提交进度）。
- 效果：同一份快照 578.8s → 541.9s，且**落库结果逐项一致**（542→505、16,417 原生值、3,428 处修正）。

|---|---|---|
| 全库未知难度 | 542 | **505**（补上 37） |
| 全库缺原生难度 | 19,165 | **2,748**（补上 16,417） |
| 过时难度值被修正 | — | **3,428 行**（CF 为主，含 atcoder 926→1455 这类） |

补上的 37 个难度：CF 26、牛客 7、QOJ 4（牛客/QOJ 与 §2.1、§3 的预估逐项吻合）。

**幂等性验证**：在已收敛的快照上再跑一次 → 难度/原生缺口与修正数**全部为 0 变化**，
即重复点击不会反复改写数据。

力扣分页 ≈ 15s。牛客整表是本轮新增的 ~120s 成本，换来 351 个原生值 + 280 处过时难度修正

### 7.6 修正一处旧结论：CF「492 道全是 gym」不准确

回填后 CF 剩余 466 道未知难度的真实构成是：**115 道 gym**（`problemset.problems` 完全不含 gym，
无来源）+ **351 道官方未评级常规题**（如 1116 的 Q# 量子题 —— 官方 API 收录但没有 `rating` 字段，
回填如实记 `missing`，不臆造）。原先「492 道 gym」是把 `100153A` 这类无短横线题号用
`INSTR(problem_key,'-')` 切分导致的误分类（`SUBSTR(x,1,-1)=''` → 判成非 gym）。

### 7.7 用户反馈修正：跑完回填「QOJ 还是没难度标签」（2026-09-27 追加）

**现象**：用户跑完一键回填后，QOJ（及部分平台）仍无难度标签。
**排查**（实测取证，不靠推断）：

1. 用户运行中的实例由 `server/config.json`（gitignored）指向 **`videos/edit/demo-data/data/icpc.db`**
   （录屏演示库，14,394 题、含 7 道 QOJ），而不是我上一轮修复的 `server/data/icpc.db`。
2. 该库里 QOJ 7 道全部 `difficulty_scale='none'`、`difficulty_source='sync'` —— **一行都没被回填过**；
   而 `backfill` 来源的行只有 atcoder 10 + CF 313。
3. 进程侧取证：dev 服务以 `tsx watch src/index.ts` 运行，**在 17:53:26 重启过一次**（文件变更触发），
   而那正是回填进行中 —— 重启杀掉了进程；重启后该进程无任何对外连接（`Get-NetTCPConnection` 为空）。
4. 单独验证 QOJ 链路本身**是好的**：在 app 等价条件（`throttledFetch` + `config.dataDir`）下
   `resolveIcpcDifficulty` 18.1s 返回 4 条（20016/20019/20021/20028），另 3 道（2513-14301/02/03）
   确实不在 `xcpcrating` 审核目录内 → 保持未知（与 §3 结论一致）。

**根因**：平台按 `pickBackfillTargets` 的 `ORDER BY platform` = **字母序**处理，而 qoj 排在最后；
最慢的牛客整表（≈400s）与洛谷逐题（≥4s/题）夹在中间。于是**一次被中断的回填**（放弃、
或开发期 `tsx watch` 因文件变更重启）留下「先跑完的平台有数据、后面的平台一行没写」——
用户看到的就是 qoj 全空。

**修法**：新增 `PLATFORM_ORDER`，按**实测成本升序**处理平台
（qoj ≈18s → atcoder ≈3s → 代码源 ≈8s → CF ≈10s → 力扣 ≈53s → 计蒜客 ≈276s → 洛谷 → 牛客）。
即使被打断，用户也已拿到绝大多数平台的标签；qoj 在头几秒完成。

**顺带把节奏钉死**（用户同时反馈「0.3 秒/题、0.45 秒/题 频率太快，容易风控」）：
- 那条文案在 `client/src/pages/Problems.tsx`，写的是适配器自带 sleep（洛谷 0.3s/题、牛客 0.45s/题），
  而线上真正的节奏是全局限速层（洛谷 4s、牛客 2s）—— 文案既过期（牛客已是整表扫描）又**低估了真实间隔**。
  已改为「全局按域名限速」的真实数值 + 平台拆分 + 指向设置页 1×–5× 调速。
- 适配器自带 sleep 全部抬到 `HOST_MIN_INTERVAL_MS` 的安全下限（`FLOOR_MS`）：
  洛谷逐题 300ms → 4000ms、牛客整表页间 500ms → 2000ms（新增 `BankFetchOptions.pageDelayMs`）、
  代码源 400→1500、力扣 400→1500、计蒜客 300→1500、AtCoder 1000→2000。
  因为「节流间隔是下限而非叠加」（取较大者），**线上不会额外变慢**；但任何不走节流层的路径
  （本地脚本、单测、未来重构遗漏）也不会再打出风控级频率 —— 这正是本轮实测踩到的坑
  （脚本直连时牛客 200 页按 0.5s/页连发）。

**验证**：用户实际库（demo-data）重跑 → **QOJ 7 道中 4 道补齐**（`icpc-tier`，开跑数秒内完成）、
全库未知难度 427 → 423 起继续收敛；新增 3 条回归测试（平台顺序、洛谷节奏下限、`pageDelayMs` 生效）。

**运维提醒**：一次回填可能跑十几分钟且是同步进行；写入是分批提交的，所以中途放弃/服务重启
只损失当前平台未提交的一批，再点一次继续即可。开发期改代码会触发 `tsx watch` 重启，
**不要在回填进行中改文件**。

## 8. 第三轮：无难度负缓存（2026-09-27 追加，补 §7.8 的唯一遗留项）

### 8.1 动机与实测缺口

`server/data/icpc.db` 19,196 行里，回填每轮仍会选中的缺口行 **4,028**（难度为空 505、缺原生值合计、
无标签 1,546）。其中**上游确实给不出**的部分（牛客空难度格 30、洛谷「暂无评定」、CF gym 115 +
官方未评级 351、计蒜客 2）性质上是稳定的，但每轮都重新问一遍：既白花请求，又让整表扫描的
`wantKeys` 早停**永远无法触发**（这些键留在目标集合里 → 牛客每次翻满 200 页 ≈400 秒）。

### 8.2 设计：两列，而不是一张新表

`problems.gap_state`（CSV 维度集合 `difficulty` / `tags`）+ `gap_checked_at`（ISO 时刻），TTL 30 天。

- **为什么放在 `problems` 上**：目标选择（`SELECT ... FROM problems WHERE 有缺口`）与题目列表展示
  都要读它，另建表就得每处 LEFT JOIN；而且删题时缓存随行走，不会留下「恢复后仍被锁 30 天」的孤儿记录。
  与 `native_difficulty` / `difficulty_source` 同一批列，迁移写法一致。
- **`difficulty` 维度同时覆盖原生原文**：上游给不出评级时，原生值与映射值是同一个 raw 值算出来的，
  必然同时无解，分两个维度只是噪声。
- **TTL 只随「新增判定」顺延**：本轮没有带来新判定时保留旧时刻。否则一个维度会靠另一个维度的
  活动无限续命，「过期重查」永远不会发生（`nextGapState` 有专门一条回归测试钉住这点）。
- **上游后来给了值 → 立即退出缓存**，不必等 TTL。

### 8.3 三条「不敢缓存」的边界（这一节是本次实现的主要风险点）

| 情形 | 是否缓存 | 原因 |
|---|---|---|
| 上游返回该题、`difficulty` 为空 | ✅ 记 `difficulty` | 明确定论（CF 未评级、牛客空格、洛谷暂无评定） |
| 上游返回该题、无标签来源 | ✅ 记 `tags` | 同上（AtCoder/kenkoooo 只有难度是永久事实） |
| 整表未命中，且来源是**单次响应即完整题库**（CF / AtCoder） | ✅ 记 `difficulty` | `problemset.problems` 不含 gym 是结构性的 |
| 整表未命中，来源是**分页扫描**（牛客 / 代码源 / 力扣 / 计蒜客） | ❌ | 本次只翻到页数上限，「没翻到」≠「上游没有」 |
| 洛谷逐题 404 / 任何请求失败 | ❌ | 404 可能就是 C3VK 风控页，缓存它等于一次封号锁 30 天 |
| QOJ 一切 null | ❌ | 分不清「xcpcrating 目录没有」和「榜单源不可用 / 本轮榜单配额满」；整表一跳才 ≈18 秒 |

**顺带修掉的一个既有缺陷**：`platformTable` 原先把「整表拉取失败」和「表里没有这道题」压成同一个
`null`。在旧语义下这无所谓（两种都记 failed），但一旦要拿「未命中」当缓存依据，风控期间的整表失败
就会把该平台所有题锁 30 天。现改为**失败即抛**（拒绝的 promise 同样被缓存，不会逐题重打上游），
两种语义分开。

### 8.4 展示

`GET /api/problems{,/page}` 新增派生字段 `difficultyGap`（负缓存记了 `difficulty` 维度 + 未过期 +

横杠回到它本来的含义 = 「还没查到」。回填结果新增 `cached`，前端文案「N 题维持『无官方难度』
