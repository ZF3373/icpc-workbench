## 一、设计目标与原则

这套接口要解决的是一个具体问题：**云端不能持有用户的平台 Cookie，也不能用云端 IP 代替用户去抓数据**，
但仍要让用户看到自己的刷题记录。

四条原则决定了下面所有设计：

1. **薄脚本，厚服务端。** 脚本只负责「用用户当前会话取原始数据 + 上报」；
   解析、归一化、去重、难度映射全部留在服务端，复用 `server/src/adapters/` 的现有逻辑。
   平台改版时坏掉的通常是**解析**（字段改名、HTML 结构变），不是 URL——
   把易变的部分放在服务端，脚本才能长期不用更新。
2. **凭据不出浏览器。** 脚本不读取、不保存、不上传平台密码与 Cookie；
   请求由浏览器同源发出，Cookie 由浏览器自动携带，脚本代码里根本看不到它。
3. **服务端掌握节流预算。** 单次同步能拉多少、多久能再拉一次，由服务端决定并下发，
   不信任脚本的自律。上千人规模下，这是防止个别用户把整个域名拖进风控的关键。
4. **幂等。** 重复上报不产生重复数据，会话中断可安全重来。
   `submissions` 表已有 `UNIQUE(user_id, platform, external_id)`，这是幂等的天然基础。

## 二、角色与信任边界

```
┌────────────────────┐
│ 用户浏览器          │
│  ┌──────────────┐  │   同源请求（Cookie 自动携带，脚本不可见）
│  │ 用户脚本      │──┼──────────────────────────────▶ 平台站点
│  │ (Tampermonkey)│  │
│  └──────┬───────┘  │
└─────────┼──────────┘
          │ HTTPS + 代理令牌（GM_xmlhttpRequest，绕过 CORS/CSP）
          ▼
   ┌─────────────────┐
   │ 云端 /api/agent │  ← 只收「原始载荷」，不碰 Cookie
   └─────────────────┘
```

三方各自的权限边界：

| 角色 | 能做 | 不能做 |
|---|---|---|
| 用户脚本 | 读当前平台页面的登录 uid；用页面会话请求平台接口；上报原始载荷 | 读平台密码 / Cookie；读其他用户数据；写任何非本人数据 |
| 代理令牌 | 只能调 `/api/agent/*`；只能操作签发它的那个 `user_id` 的数据 | 调业务 API；读同步历史以外的东西；跨用户操作 |
| 云端 | 存原始载荷、解析、入库、记录同步历史 | 持有平台 Cookie；代表用户向平台发起请求 |

**明确不做的事**：云端不保存用户脚本抓到的原始载荷（解析完即丢），
避免把平台页面内容沉淀成一份额外副本。

## 三、授权握手时序

### 3.1 首次连接

```
用户脚本(平台页面)          云端                        用户
     │                       │                          │
     │ 点「连接」             │                          │
     │ 生成 state(32B 随机)   │                          │
     │ 生成/读取 clientId     │                          │
     │ （UUID，存 GM_setValue，│                          │
     │   同一浏览器长期不变）   │                          │
     │ window.open ──────────▶ /agent/authorize           │
     │                       │  state=…&platform=luogu   │
     │                       │                          │
     │                       │  未登录 → 走登录页 ──────▶ │
     │                       │  ◀──────── 登录完成        │
     │                       │                          │
     │                       │  展示：云端账号 / 绑定平台 │
     │                       │  / 风险提示 ─────────────▶ │
     │                       │  ◀──────── 点击「确认连接」│
     │                       │                          │
     │                       │ POST /api/agent/authorize │
     │                       │ → 签发一次性 code(60s)     │
     │                       │                          │
     │ ◀── postMessage({state, code}) ── 授权页           │
     │ 校验 state 一致        │                          │
     │ POST /api/agent/token ─▶ 用 code+clientId 换令牌    │
     │                       │ 按 (user, clientId) upsert│
     │ ◀── { token, expiresAt } ──────────────────────── │
     │ GM_setValue 保存       │                          │
     │ 面板显示「已连接」      │                          │
```

**为什么用「一次性 code 换令牌」而不是直接 postMessage 令牌原文**：
`postMessage` 的目标窗口是洛谷页面，理论上可能被页面上的其他脚本监听到。
一次性 code 有效期 60 秒、只能兑换一次，且必须由脚本自己发起 HTTPS 请求才能换成令牌——
即便被截获，攻击者也需要能向我们的域名发请求才用得上，风险显著更低。

**state 的作用**：防跨站伪造授权。脚本保存 `state`，收到 `postMessage` 后必须比对一致才继续。

**兜底路径**：弹窗被拦截时，授权页显示一段可复制的令牌，
用户在脚本面板里手动粘贴即可。这种情况下脚本会把**自己的 `clientId`**
一并在首次请求时上报，服务端据此把这条令牌归到该浏览器名下
（若设置页直接生成令牌，则由服务端分配一个 `clientId`，
`label` 记为「手动生成」，脚本粘贴后自动接管该行）。

### 3.2 已连接后的日常同步

```
脚本                    云端
 │ GET /api/agent/sync/context?platform=luogu
 │───────────────────────▶ 返回 sessionId / 已知最新提交号 / 节流预算
 │
 │ 在平台页面内翻页取数（同源，Cookie 自动携带）
 │ 命中「已知最新提交号」即停 ← 增量早停
 │
 │ POST /api/agent/sync/ingest  { sessionId, captures:[…] }
 │───────────────────────▶ 解析 → 入库 → 返回 { imported, continue }
 │ ◀─────────────────────── continue=false 时脚本停止翻页
 │
 │ POST /api/agent/sync/ingest  { sessionId, done:true }
 │───────────────────────▶ 收尾，写 sync_runs
```

**增量早停是这套设计里最重要的性能与安全机制**：稳态下每次同步只需 1 页请求，
而不是把历史全翻一遍。全量回填是最像爬虫的行为，必须避免。

### 3.3 handle 从哪来，以及账号一致性校验

**取数用的 handle 由服务端下发**（`/sync/context` 返回 `handleBound`，
即 `platform_accounts.handle`）。脚本不猜、不拼，直接用它构造请求 URL。
这样脚本不需要读取任何平台页面的内部变量就能工作——平台改版换掉页面全局也不会坏。

**页面身份读取是「尽力而为」的附加校验**，对应参考站点注意事项里
「请确认登录的是已绑定到云端的账号」那一条：

- 脚本尽力从当前页面读出「现在登录的是谁」（各平台做法不同，见第六节），
  随请求带上 `observedHandle`。
- 读到了且与 `handleBound` 不一致 → 409 `HANDLE_MISMATCH`，
  脚本提示「当前登录的是账号 A，云端绑定的是账号 B，请切换账号或到设置页重新绑定」。
- 读到了但明显是未登录状态 → 409 `NOT_LOGGED_IN`。
- **读不到就跳过这项校验，不阻塞同步**——页面内部变量没有稳定契约，
  把它做成硬性前置会让脚本在平台每次改版后彻底不可用。

## 四、云端 API

### 4.1 通用约定

**鉴权**：除 `POST /api/agent/authorize`（用会话 Cookie）外，其余接口一律用代理令牌：

```
Authorization: Bearer <agentToken>
X-Agent-Version: 0.1.0
```

**令牌形态**：`icpc_agent_<32字节 base64url>`，服务端只存 SHA-256 哈希，
与用户会话体系完全隔离，可在设置页单独吊销。

**版本协商**：每个请求都带 `X-Agent-Version`。低于服务端 `MIN_AGENT_VERSION` 时，
除 `GET /api/agent/userscript/latest` 外的所有接口返回 `426 AGENT_OUTDATED`，
响应体附最新版下载地址——避免老脚本产生难解释的解析失败。

**错误响应统一形状**：

```jsonc
{
  "error": "人类可读的中文说明",
  "code": "MACHINE_READABLE_CODE",
  "detail": { }        // 可选，结构化补充信息
}
```

### 4.2 错误码表

| code | HTTP | 含义 | 脚本侧应有行为 |
|---|---|---|---|
| `UNAUTHORIZED` | 401 | 令牌缺失 / 无效 / 已吊销 | 清除本地令牌，提示重新连接 |
| `AGENT_OUTDATED` | 426 | 脚本版本低于服务端最低要求 | 提示「请更新脚本」并打开安装页 |
| `CAPTURE_KIND_UNKNOWN` | 400 | 服务端不认识某个 `kind` | 同上（说明协议不匹配） |
| `HANDLE_MISMATCH` | 409 | 当前登录账号与云端绑定不一致 | 提示切换账号或重新绑定 |
| `NOT_LOGGED_IN` | 409 | 平台页面取不到登录态 | 提示先登录平台 |
| `PLATFORM_NOT_BOUND` | 409 | 云端尚未绑定该平台账号 | 引导去设置页绑定 |
| `AGENT_REQUIRED` | 409 | 云端模式不允许服务端直连该平台 | 引导安装脚本 |
| `RATE_LIMITED` | 429 | 超过服务端同步频率上限 | 展示 `detail.nextAllowedAt` |
| `SESSION_EXPIRED` | 409 | `sessionId` 过期或不存在 | 重新走 `/sync/context` |
| `PAYLOAD_TOO_LARGE` | 413 | 单次上报超过体积上限 | 减小批量后重试 |

### 4.3 `POST /api/agent/authorize`

签发一次性授权码。由授权页调用，**用会话 Cookie 鉴权**（不是代理令牌）。

```jsonc
// 请求
{ "platform": "luogu", "state": "abc…" }

// 响应 200
{
  "code": "one_time_code_…",
  "expiresAt": "2026-09-19T12:01:00.000Z"   // 60 秒后过期
}
```

服务端在此处校验：用户在云端已登录、`platform` 合法。
**不校验平台 handle**——handle 在第一次同步时由脚本上报并经 3.3 的比对确定。

### 4.4 `POST /api/agent/token`

用一次性 code 换长期令牌。**不需要鉴权头**（code 本身就是凭据）。

```jsonc
// 请求
{
  "code": "one_time_code_…",
  "clientId": "8f3c1a2e-…",        // 浏览器侧生成的 UUID，存 GM_setValue，长期不变
  "clientKind": "userscript",      // userscript | desktop（见 4.9）
  "label": "Chrome · Windows"      // 可选，缺省由服务端按 UA 生成
}

// 响应 200
{
  "token": "icpc_agent_…",
  "expiresAt": null,          // null = 长期有效，直到主动吊销
  "tokenId": 17,              // 设置页吊销用
  "platformScope": ["luogu", "nowcoder"],
  "user": { "id": 42, "username": "alice" }
}
```

code 用过即失效；过期、重复使用均返回 `UNAUTHORIZED`。

**令牌粒度 = 每浏览器一个**（决策 4）。服务端按 `(user_id, client_id)` 做 upsert：

- 同一浏览器重新连接 → **换发新令牌并作废该行旧令牌**，不堆积重复条目。
  用户换了浏览器或清了扩展数据才会多出一行。
- `label` 用于设置页展示；缺省取 UA 里的浏览器 + 操作系统（如「Chrome · Windows」）。
- 因此「重新连接」既是修复手段，也是一键换新令牌的方式。

### 4.5 `GET /api/agent/tokens` / `DELETE /api/agent/tokens/:id`

设置页「已连接的同步脚本」列表与吊销。返回**不含令牌原文**，
每行对应一个浏览器（或一个桌面客户端）：

```jsonc
{
  "tokens": [
    {
      "id": 17,
      "clientKind": "userscript",       // userscript | desktop
      "label": "Chrome · Windows",
      "createdAt": "2026-09-19T12:00:00.000Z",
      "lastUsedAt": "2026-09-19T18:30:00.000Z",
      "userAgent": "Mozilla/5.0 …"
    }
  ]
}
```

`DELETE /api/agent/tokens/:id` 吊销单个浏览器，幂等；吊销后该客户端的下一次请求立即 401。

### 4.6 `GET /api/agent/sync/context`

同步前握手：拿会话 id、已知游标与节流预算。

```jsonc
// 请求
GET /api/agent/sync/context?platform=jisuanke&handle=123456&trigger=manual
//   trigger: manual（用户点「同步」）| auto（定时器触发）；缺省 manual
// 可选：observedHandle=123456（脚本从页面读到的当前登录身份，读不到则省略）

// 响应 200
{
  "sessionId": "s_8f3c…",
  "expiresAt": "2026-09-19T12:10:00.000Z",
  "platform": "jisuanke",
  "handleBound": "123456",
  "observedHandle": "123456",   // 省略 = 脚本未能读取，服务端跳过一致性校验

  // 增量早停依据：库中该平台最新的提交号（按时间倒序取第一条）
  "knownNewestExternalId": "1a2b3c4d",
  "knownCount": 1842,

  // 本次补全起点：上次被截断时为非 1，脚本从该页开始翻
  "startPage": 1,

  // 取数分段：脚本按数组顺序逐段执行，每段各自遵守自己的预算与节流
  "segments": [
    {
      "id": "contests",
      "enabled": true,
      "budget": { "maxNewItems": 300, "maxPages": 30, "maxCaptures": 30 },
      "throttling": { "pageDelayMs": 1500, "jitterRatio": 0.3 }
    },
    {
      "id": "practice",
      "enabled": true,
      "budget": { "maxNewItems": 100, "maxPages": 10, "maxCaptures": 10 },
      "throttling": { "pageDelayMs": 2000, "jitterRatio": 0.4 }
    }
  ]
}
```

`handle` 与 `platform_accounts.handle` 不一致时返回 `HANDLE_MISMATCH`；
未绑定则返回 `PLATFORM_NOT_BOUND`。

**分段（segment）的规则**：

- 单段平台（洛谷 / 牛客 / 代码源 / LeetCode）只有一个 segment，`id` 固定为 `default`。
- 计蒜客分 `contests`（比赛提交）与 `practice`（自由练题）两段，
  对应现有服务端同步的两条路径（见 `server/src/adapters/jisuanke.ts`）。
- **`practice` 段在 `trigger=auto`（定时同步）时默认 `enabled: false`**，
  只有用户手动点「同步」才跑。练习段是「预筛 `/api/problems` + 逐题取提交」的扇出流程，
  请求量远大于比赛段，把它从自动同步里摘出去是降低频率最有效的一招。
- 练习段单独配置更长的 `pageDelayMs`（2000ms，比赛段 1500ms）与更小的预算
  （新增 100 条 / 10 页，比赛段 300 条 / 30 页）。
- `jitterRatio` 表示实际等待 = `pageDelayMs × (1 ± ratio)`，用于去掉机械节奏。
- 脚本**不得越过** `budget`；服务端在 ingest 侧另有一道硬校验。

### 4.7 `POST /api/agent/sync/ingest`

上报原始载荷。**可多次调用**，脚本每积累若干页就提交一批。

```jsonc
// 请求
{
  "sessionId": "s_8f3c…",
  "platform": "jisuanke",
  "handle": "123456",
  "segment": "practice",                // 当前正在取的段；单段平台填 "default"
  "done": false,
  "captures": [
    {
      "kind": "jisuanke.problemSubmissions",   // 契约核心：声明载荷形状
      "url": "https://www.jisuanke.com/api/problem/submissions?problemId=123&page=1",
      "status": 200,
      "payload": { /* 平台原始响应：JSON 对象，或 HTML 字符串 */ }
    }
  ]
}

// 响应 200
{
  "imported": 18,
  "skipped": 2,
  "newItems": 18,        // 本段累计新增（脚本展示进度用）
  "continue": true,      // false = 本段已达预算，脚本停止翻本段
  "segmentDone": false,  // true = 本段可取的数据已取完（自然结束，非预算截断）
  "done": false,
  "note": null           // 可选的可读提示（如「已到单次上限，下次继续补全」）
}
```

`done: true` 的请求收尾本次会话：写 `sync_runs` 行、
更新 `platform_accounts.last_sync_at` 与 `sync_truncated`。

脚本按 `segments` 顺序推进：某段 `continue=false` 或 `segmentDone=true` 时换下一段；
全部段跑完（或都被跳过）后发一个 `done: true` 的收尾请求。
段级预算由服务端按 `(session, segment)` 独立计数，脚本自报的数字不参与判定。

**幂等**：重复上报同一批 captures 时，`skipped` 增加、`imported` 不变。
会话过期（`SESSION_EXPIRED`）后脚本重新走 context 即可，不会产生重复数据。

### 4.8 `GET /api/agent/userscript/latest`

```jsonc
{
  "version": "0.1.0",
  "minVersion": "0.1.0",
  "downloadUrl": "https://<域名>/agent/icpc-sync.user.js",
  "installUrl": "https://<域名>/agent/install",
  "notes": "支持洛谷、牛客、代码源、LeetCode、计蒜客",
  "publishedAt": "2026-09-19T00:00:00.000Z"
}
```

脚本启动时与每 6 小时检查一次；`version < minVersion` 时在面板上显著提示。

### 4.9 为桌面客户端预留的接入点（决策 3）

本轮**不做**「脚本指向本地桌面版」——脚本只连云端。
但要为「桌面版后续登录云端账号、直接同步状态」留好位置，避免将来回头改协议。

已经预留的部分：

- **`clientKind` 字段**（4.4）：取值 `userscript` | `desktop`。
  设置页据此区分展示；服务端也可对两类客户端施加不同策略
  （桌面端可后台常驻，允许更长的同步间隔与更大的单次预算）。
- **协议与客户端类型无关**：桌面版接入时复用同一套
  `/api/agent/token` + `/api/agent/sync/context` + `/api/agent/sync/ingest`，
  只是取数发生在 Node 侧（直接复用 `server/src/adapters/`），而不是浏览器页面内。
  4.7 的 capture 契约在这里体现价值：**同一份 `kind` 表，两种取数环境共用一套解析**。
- **`sync_runs.triggered_by` 预留 `agent` 值**：脚本 / 桌面端驱动的同步在同步中心里
  与 `manual` / `all` / `retry` 区分开。定时触发的记 `agent`，
  用户手动点的记 `agent-manual`——自动同步被限流时不该和用户主动操作混在一起统计。

桌面版真正接入时唯一需要新增的是**授权获取方式**：桌面应用没有页面可以
`postMessage`，届时让它打开系统浏览器访问同一个 `/agent/authorize` 页面，
用同一套一次性 code 换令牌即可。若届时觉得体验不够，再补一个设备码轮询流程。

**本轮不改的部分**：桌面版保持现状（本地单机模式），不引入令牌、不与云端通信。

## 五、数据契约：capture 类型表

`kind` 是脚本与服务端之间**唯一的强契约**。服务端为每个 `kind` 注册一个纯解析函数，
未知 `kind` 一律拒绝（`CAPTURE_KIND_UNKNOWN`），从机制上防住协议错配。

| kind | 段 | payload 形状 | 对应解析来源 |
|---|---|---|---|
| `luogu.recordList` | default | JSON 对象（`currentData.records[]`） | `server/src/adapters/luogu.ts` |
| `nowcoder.practiceCodingHtml` | default | HTML 字符串（提交表格） | `server/src/adapters/nowcoder.ts` |
| `daimayuan.recordJson` | default | JSON 对象（Hydro rdocs 数组） | `server/src/adapters/daimayuan.ts` |
| `leetcode.submissionList` | default | JSON 对象（GraphQL data） | `server/src/adapters/leetcode.ts` |
| `jisuanke.contests` | contests | JSON 对象 | `server/src/adapters/jisuanke.ts` |
| `jisuanke.contestSubmissions` | contests | JSON 对象 | 同上 |
| `jisuanke.problems` | practice | JSON 对象 | 同上 |
| `jisuanke.problemSubmissions` | practice | JSON 对象 | 同上 |
| `qoj.submissionsHtml` | default | HTML 字符串 | `server/src/adapters/qoj.ts` |

> **QOJ 本轮不启用**（决策 1）：`qoj.submissionsHtml` 这个 kind 先保留在表里、
> 但注册表标记为未启用，脚本也不实现它的 fetcher。原因是浏览器内是否仍需
> HTTP/1.1 未经实测（现有适配器为绕开 Cloudflare 对 h2 的托管挑战而走 HTTP/1.1，
> 见 `server/src/adapters/http1.ts`）。QOJ 用户本轮走手动导入，
> 待实测通过后再把该 kind 打开即可，协议无需改动。

解析后的中间结构就是现有的 `NormalizedSubmission`（`shared/src/index.ts:81`），
入库走现有的 `insertNormalized`（`server/src/import/importService.ts:22`）——
**入库路径与今天完全一致**，难度映射、题目 upsert、来源优先级都不用改。

**体积限制**：单次 `ingest` 请求体 ≤ 4 MiB（JSON）或 8 MiB（含 HTML），
超出返回 `PAYLOAD_TOO_LARGE`。脚本按「累计 1 MiB 或 5 页」先到先发。

## 六、脚本侧取数清单

每个平台一个 fetcher 模块，只做「拼 URL + 翻页 + 判断何时停」。
**不做任何字段解析**。handle 一律从当前页面读出，不用用户手输。

| 平台 | `@match` | 取数端点 | handle 来源 | 翻页与早停 |
|---|---|---|---|---|
| 洛谷 | `www.luogu.com.cn/*` | `GET /record/list?user={handle}&page=N`<br>请求头 `x-lentille-request: content-only` | 服务端下发 | 新→旧；整页命中已知提交号即停 |
| 牛客 | `ac.nowcoder.com/*` | `GET /acm/contest/profile/{handle}/practice-coding?pageSize=10&page=N&search=&statusTypeFilter=-1&languageCategoryFilter=-1&orderType=DESC` | 服务端下发 | 新→旧；同上 |
| 代码源 | `bs.daimayuan.top/*` | `GET /record?uidOrName={handle}&page=N`<br>请求头 `Accept: application/json` | 服务端下发 | 新→旧；同上 |
| LeetCode | `leetcode.cn/*` | `POST /graphql`，`submissionList` 查询 | 服务端下发 | 按 offset 翻页；同上 |
| 计蒜客 | `www.jisuanke.com/*` | **contests 段**：① `GET /api/contests?page=N&hasParticipated=true`<br>② 逐赛 `GET /api/contest/submissions?contestId=`<br>**practice 段**：③ `GET /api/problems?page=N&status=passed\|attempted`<br>④ `GET /api/problem/submissions?problemId=&page=N` | 服务端下发 | 两段独立推进；③→④ 是扇出流程，按题目序号做游标 |

**v1 覆盖 5 个平台**：洛谷 / 牛客 / 代码源 / LeetCode / 计蒜客。
**QOJ 不进 v1**（决策 1），用户走手动导入；`qoj.submissionsHtml` 保留待启用。

> **页面身份读取待实测。** 上表「handle 来源」一律是服务端下发，
> 所以脚本的**取数路径不依赖任何页面全局变量**。仅 3.3 的「账号一致性提醒」
> 需要读取当前登录身份，各平台实现方式不同（页面全局变量 / 用户菜单 DOM / 个人页链接），
> 且**平台改版就可能失效**。实现时需逐平台实测确认，读不到时降级为跳过校验。
> 这是脚本里最脆弱的一环，也是把它设计成「尽力而为」而非硬性前置的原因。

**AtCoder / Codeforces 不在此表**：两者走官方 / 社区公开 API，由云端直连
（见方案第三节方案 2）。若日后跨境链路实测不达标，可平移进本表，
协议无需改动——只需新增两个 `kind`。

**为什么计蒜客的编排放在脚本而不是服务端下发**：
它是「先取比赛列表、再逐赛取提交」的动态扇出，做成服务端下发的声明式计划
会引入一个小型 DSL，对 v1 不划算。代价是这个平台的 fetcher 稍厚（约 60–80 行），
但**解析仍在服务端**——而解析才是真正易变的部分。

**计蒜客的取数节奏**（决策 2：练习段默认开，但降频）：

- `practice` 段默认开启（与服务端 `settings['jisuanke.practiceSync']` 缺省为 true 一致），
  但**定时同步时服务端会把它关掉**，只在用户手动点「同步」时跑（见 4.6）。
- 练习段 `pageDelayMs = 2000ms`、预算 100 条 / 10 页；
  比赛段 `pageDelayMs = 1500ms`、预算 300 条 / 30 页。
- 练习段 ③ 的预筛（`status=passed` / `status=attempted` 两轮）本身就要翻多页，
  脚本需把两轮都算进 `maxPages` 预算，不得因为「还没进 ④」就自行放宽。

## 七、脚本行为规范

### 7.1 面板状态机

```
未安装 → 未连接 → 已连接(空闲) → 同步中 → 已连接(空闲)
                      │                     │
                      └──── 错误态 ─────────┘
```

面板需要展示：连接状态、当前云端账号、绑定平台、上次同步时间与结果、
同步间隔选择（1–12 小时 / 不自动）、手动「同步」按钮、进度（第 N 页 / 已入库 M 条）、
错误提示与对应操作（更新脚本 / 重新登录平台 / 重新连接）。

### 7.2 定时同步

- 默认**不自动同步**，由用户显式选择间隔（1–12 小时），默认建议 6–12 小时。
- 只在平台页面打开时运行；页面关闭即暂停（这是用户脚本的固有限制，需在 UI 说明）。
- 同步中不响应新的定时触发（单飞）。
- 定时触发一律带 `trigger=auto`：服务端会把重段（计蒜客 `practice`）标记为
  `enabled: false`，脚本照做即可，**不要在客户端自行决定跑不跑**。
  用户手动点「同步」时带 `trigger=manual`，此时才会跑全部分段。
- 服务端 `RATE_LIMITED` 时，脚本暂停自动同步直到 `detail.nextAllowedAt`。

### 7.3 失败处理

| 情况 | 脚本行为 |
|---|---|
| 平台返回 403 / 跳登录页 | 停止本次同步，提示「请确认已登录并稍后再试」；**不重试** |
| 平台返回 429 | 停止，按 `Retry-After` 或 30 分钟后再试 |
| 页面结构取不到 handle | 提示「脚本可能已过期，请更新后重试」 |
| 服务端 426 | 提示更新脚本，附安装链接 |
| 网络失败 | 指数退避重试 ≤ 3 次，仍失败则提示 |

**明确不做重试轰炸**：任何 403/429 一律立即停止，
与现有 `syncScheduler` 的「鉴权失败立即停止」策略保持一致。

### 7.4 安全要求（写进脚本实现约定）

- **零第三方依赖**，脚本内不 `eval`、不动态 `import()` 远程代码。
- 上报只走 `GM_xmlhttpRequest`，`@connect` 只声明我们自己的域名。
- 令牌只存 `GM_setValue`，不写 `localStorage`（避免被页面脚本读到）。
- 不读取、不缓存、不上报任何 Cookie 值。

### 8.1 新增文件

| 文件 | 职责 |
|---|---|
| `server/src/routes/agent.ts` | 第 4 节的 7 个端点 |

新增一张表（幂等迁移，照 `server/src/db/index.ts` 现有范式）：

```sql
CREATE TABLE IF NOT EXISTS agent_tokens (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id      INTEGER NOT NULL REFERENCES users(id),
  client_id    TEXT NOT NULL,          -- 浏览器生成的 UUID
  client_kind  TEXT NOT NULL DEFAULT 'userscript',  -- userscript | desktop
  label        TEXT NOT NULL DEFAULT '',
  token_hash   TEXT NOT NULL,          -- 只存 SHA-256，不存原文
  user_agent   TEXT,
  created_at   TEXT NOT NULL DEFAULT (datetime('now')),
  last_used_at TEXT,
  revoked_at   TEXT,
  UNIQUE (user_id, client_id)          -- 决策 4：每浏览器一行

```

### 8.2 适配器重构：把「解析」从「取数」里拆出来

当前 `PlatformAdapter.fetchUserSubmissions` 同时做了两件事（取数 + 解析）。
Phase 4 需要把它拆成两个纯函数，两边共用：

```ts
// 现有（保持不变，服务端直连 CF/AtCoder 与本地模式继续用）
fetchUserSubmissions(handle, opts): Promise<NormalizedSubmission[]>

// 新增：从一份原始载荷解析出提交（纯函数，无网络）
parseCapture(kind: CaptureKind, payload: unknown, ctx: { handle: string }): NormalizedSubmission[]
```

`fetchUserSubmissions` 内部改为调用 `parseCapture`，保证**解析逻辑只有一份**。
这是本阶段唯一有风险的改动，需要为每个平台补一条「同一份样本 → 两条路径结果一致」的测试。

### 8.3 云端模式开关

新增配置 `mode: 'local' | 'cloud'`（默认 `local`，保持桌面版行为不变）。

`server/src/routes/sync.ts` 的 `POST /api/sync/:platform` 在 `cloud` 模式下：

- 放行 `codeforces` / `atcoder`
- 其余平台返回 `409 AGENT_REQUIRED`，`detail` 带脚本安装页地址

前端据此把「同步」按钮换成「安装同步脚本」引导，而不是弹错误。

### 8.4 会话与同步历史

v1 用**进程内 Map** 保存会话：`sessionId`、`userId`、`platform`、`trigger`、
**每个 segment 各自的新增计数与页码进度**、过期时间（TTL 10 分钟）。
收尾时写一行 `sync_runs`，让脚本驱动的同步与手动同步在「同步中心」里表现一致。

代价：服务重启会丢掉进行中的会话，脚本收到 `SESSION_EXPIRED` 后重新开始——
因为幂等，这只是多一次请求，没有副作用。

### 8.5 节流维度改造

`server/src/net/hostThrottle.ts` 目前只按域名节流。云端模式下需要改为
「`userId:platform` 级 + 域名级」双层：前者约束单个用户，
后者保护我们的出站总量（云端直连 CF/AtCoder 时用）。
脚本侧不受此约束（请求从用户浏览器发出），但服务端仍用
`segments[].budget` 与 `RATE_LIMITED` 控制单个用户的同步频率与总量。
分段预算是**段级独立**的：`contests` 段用满不会连带截断 `practice` 段，
反之亦然——否则重段会把轻段的额度吃掉。

### 8.6 前端

- `client/src/pages/AgentAuthorize.tsx`：授权页（展示账号 / 平台 / 风险提示 / 确认按钮）。
- 设置页新增「同步脚本」卡片：安装入口、已连接脚本列表、吊销、重新生成令牌、
  图文步骤（安装 Tampermonkey → 安装脚本 → 在平台页面点连接 → 点同步）。
- 平台账号区在云端模式下，凭据类平台不再显示 Cookie 输入框，改为显示脚本连接状态。

## 九、验收清单

**协议层**

- 未带令牌调 `/api/agent/*` → 401 `UNAUTHORIZED`，响应体是 JSON。
- `X-Agent-Version` 低于最小值 → 426 `AGENT_OUTDATED`，附下载地址。
- 未知 `kind` → 400 `CAPTURE_KIND_UNKNOWN`，不写入任何数据。
- **未启用**的 kind（`qoj.submissionsHtml`）即便形状已注册，v1 也一律拒绝。
- 一次性 code 重复使用 / 超时 → 401。

**功能层**

- 完整走通：装脚本 → 平台页面点连接 → 云端授权 → 点同步 → 数据入库。
- 同一批 captures 重复上报：`imported` 不变、`skipped` 增加。
- 增量早停生效：第二次同步只请求 1 页（可断言平台侧请求数）。
- 命中 `maxNewItems` 后服务端返回 `continue:false`，脚本立即停止翻页。
- `handle` 不一致 → 409 `HANDLE_MISMATCH`，且**不写入任何数据**。
- 计蒜客 `trigger=auto` 时 `practice` 段 `enabled=false`；`trigger=manual` 时为 true。
- 分段预算独立计数：`contests` 段用满不会连带截断 `practice` 段。
- 同一浏览器重新连接 → 令牌列表行数不变（按 `(user_id, client_id)` upsert），旧令牌立即失效。
- 不同浏览器连接 → 令牌列表各占一行，吊销其一不影响另一台。

**安全层**

- 服务端日志、数据库、`sync_runs` 中均不出现任何 Cookie 值。
- 代理令牌只能写入签发它的 `user_id` 的数据（构造跨用户请求验证）。
- 令牌吊销后立即 401。
- 云端模式下 `/api/sync/luogu` 返回 `AGENT_REQUIRED`。

**回归层**

- `parseCapture` 与 `fetchUserSubmissions` 对同一份样本产出完全一致的
  `NormalizedSubmission[]`（每个平台一条用例）。
- 本地模式（桌面版）行为不变：`npm test -w server` 全绿。

## 十一、仍未决的问题

1. **用户怎么知道自己的 handle。** 本设计里取数用的 handle 由服务端下发
   （见 3.3），所以用户必须**先在设置页绑定账号**，脚本才能工作——
   但洛谷要填的是 `_uid`（一串数字），普通用户不一定知道去哪找。
   两个方向：① 设置页给出取 uid 的图文指引（与今天的 Cookie 指引同源，改动小）；
   ② 首次同步时用页面读到的 `observedHandle` 反向建议绑定（体验好，
   但依赖 3.3 那个「尽力而为」的身份读取）。**需要产品决策。**
2. **令牌是否设过期时间。** 当前设计是长期有效直到主动吊销。
   更稳妥的做法是给一个上限（如 180 天）并滑动续期，代价是用户偶尔需要重新连接。
3. **`RATE_LIMITED` 的阈值。** 「多久一次算太频繁」需要产品定一个数，
   建议起步 30 分钟，观察真实使用后再调。
4. **脚本分发在国内的可达性。** `.user.js` 与安装页放在我们的域名上，
   需要保证国内网络稳定可达（与 Phase 5 的部署一起验证）。
