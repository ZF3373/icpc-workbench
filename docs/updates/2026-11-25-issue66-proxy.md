# issue #66：桌面版「本地服务未响应」的真因是系统代理接管了回环探活

## 现象

用户报告：打开工作台正常，接着打开 Claude Desktop，软件就退回「本地服务未响应」；
退出 Claude Desktop、重启工作台都打不开，**只有重启系统才能恢复**；而**直接双击
`icpc-core.exe` 却一切正常**，浏览器打开 `localhost:3001` 也正常。

用户补充的现场证据把范围缩到了很小：

- 任务管理器里 **`icpc-core.exe` 活着**（PID 2832，占用约 218 MB，CPU 00）；
- 日志停在 `[shell] 核心进程无响应超过恢复预算，强制结束后将于下轮重新拉起`；
- 但同一份日志里**没有** `[shell] 工作台壳启动`、`[shell] 服务就绪`、`[shell] 服务掉线` 这几行。

## 根因

`reqwest` 0.12 的 **`system-proxy` 是默认特性**。桌面壳的 `discovery::client()` 用的是
裸 `ClientBuilder`，于是 Windows 上会读注册表 `Internet Settings` 的
`ProxyEnable` / `ProxyServer` / `ProxyOverride`，**把发往 127.0.0.1 的健康探测也交给
系统代理**。

而 Windows 默认的旁路写法 `127.*` 在 hyper-util 的匹配器里**不起作用**——那里只把
`*` 当通配，其余条目一律按域名处理（实测：`NO_PROXY` 写 `127.*`、`localhost`、
`<local>` 全部无效，只有精确的 `127.0.0.1` 才能旁路）。

于是链路变成：

1. 核心活得好好的，`/api/health` 正常；
2. 壳的探活请求被塞进系统代理 → 代理连不上/规则拦截/端口变更 → 请求失败；
3. 壳判定「本地服务未响应」→ 按恢复预算（30s）把**正常的核心**强杀；
4. 下一轮重拉，重复上述过程 —— 用户看到的就是「反复掉线、重启系统才恢复」。

浏览器完全不受影响，因为浏览器自己就旁路 localhost —— 这正好解释了
「浏览器能开、桌面版不行」这个最迷惑人的现象。

### 复现与验证

本机临时把 `ProxyEnable` 置 1、`ProxyServer` 指向一个不可达端口，用与壳完全相同的
两种写法做 A/B：

```
BEFORE(no fix) -> ERR in 2.0246816s: error sending request for url (http://127.0.0.1:3421/api/health)
AFTER(no_proxy) -> 200 OK in 3.6752ms
```

（验证后注册表已还原。）另有旁路写法矩阵实测：`127.*` / `localhost` / `<local>`
均无法旁路回环，只有 `127.0.0.1` 可以 —— 所以受影响面是「所有开了系统代理的用户」，
不是个别配置。

## 修复

1. **`discovery::client()` 与 `shell_auth::http()` 一律 `.no_proxy()`**。
   回环地址永远不该走代理，这与用户的系统代理设置无关。
2. **日志轮转改为「每次壳运行只轮转一次」**。原先每 respawn 一次就把 `core.log`
   推到 `core.old.log`（只留一份），于是「壳启动 / 服务就绪 / 服务掉线」这些
   **最关键的因果行**会在恢复期被自己推走并覆盖 —— 这正是用户贴回的日志只剩
   「拉起 → 被杀」尾巴的原因，也让这次定位多绕了一大圈。
3. **掉线页补上代理排查提示**：明确写出「浏览器能开、只有本窗口报错 = 系统代理接管了
   本机请求」，并给出添加例外的位置。
4. **Rust 侧接入 CI 守卫**（`ci.yml` 的 `windows-preview` 与 `nightly-desktop.yml`
   的 `build-windows`）。此前 CI 对 Rust 侧**零覆盖**，这类回归没有任何拦截。

   这里没有直接在 CI 里跑 `cargo test`：本 crate 的 `build.rs` 会用 embed-resource
   编译 `windows-app.manifest`，且 tauri 构建要求 `binaries/icpc-core-<triple>.exe`
   就位。在干净 runner 上先失败的是 `rc.exe`（`RC2135 / file not found: encoding`）
   和 `resource path doesn't exist`，与测试断言无关——这一版已经踩过一次。
   所以 CI 改为**零构建依赖的静态守卫**：检查 `discovery.rs` 与 `shell_auth.rs`
   里是否仍有 `.no_proxy()`，删掉即红。断言型测试保留在 crate 内，开发机上
   `cargo test` 可跑（本机已验证：删掉修复会失败、恢复后通过）。

### 回归测试

`desktop/app/src-tauri/src/discovery.rs` 新增 `probe_ignores_system_proxy`：
起一个本地最小 HTTP 服务，把 `HTTP_PROXY` / `ALL_PROXY` 指向必然不可达的端口、
并**故意清空 `NO_PROXY`**（模拟「系统旁路列表没有回环」），断言探活仍能连上。

已验证这条测试**真的能抓出这个 bug**：临时删掉 `.no_proxy()` 后它立即失败并给出
`探活被系统代理拦截了：client() 必须调用 .no_proxy()（issue #66）`，恢复后重新通过。

CI 侧的守卫则用一条必然能跑通的静态检查兜底（见上），两者分工：断言靠 `cargo test`，
「别被人改回去」靠 CI。

## 与之前几次修复的关系

issue #66 早前已修过三处**独立成立**的脆弱点（`busy_timeout`、MCP 并发闸门、
残留核心清理 + `runtime.json`）。本次是第四个、也是**唯一真正解释用户现象**的那个：

- 之前的并发闸门针对「事件循环被占满」，但本次实测（6 个并发重查询打真实 19196 题库）
  探活最大延迟仅 **29 ms**，远达不到误杀阈值 —— 那条路径不是主因；
- 知识库索引重建实测 **848 ms**（39914 行 JSONL / 47806 条标注），同样不足以撑起 30 秒。

所以本次没有推翻之前的加固（它们仍有价值），但明确了主因在 shell 的 HTTP 客户端。

## 另附

排查中还发现 nightly 发布里堆积了 20 个历史版本产物（0.5.1–0.6.3），且 Windows 与
macOS 打出的版本号不一致（0.6.3 / 0.6.2）。这两项与 issue #66 无关，未在本次改动。
