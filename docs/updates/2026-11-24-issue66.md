# issue #66：与 Claude Desktop 同时运行后「本地服务未响应」

issue #66 的描述是「先开工作台正常，再开 Claude Desktop 就退到『本地服务未响应』，
且退出 Claude Desktop、重启工作台都打不开，重启系统后恢复正常；直接运行 icpc-core 却正常」。

先说结论：**没有复现出来**，也**没有找到任何「工作台写坏 Claude Desktop 配置」的代码**
（全仓 `claude_desktop_config` / `mcpServers` / `APPDATA` 只命中 README 示例与 NSIS 卸载备份）。
所以这轮没有改任何会让「原本正常的路径」变样的东西，只修了三处**独立成立**的脆弱点 ——
它们各自都能单独造成用户描述的现象，也都能在事后把排查线索留下来。

## 一、「本地服务未响应」到底是什么条件触发的

文案在 `desktop/app/ui/offline.html`，由 `main.rs` 的 `navigate_offline()` 加载。三处触发：

| 触发点 | 条件 |
|---|---|
| 首启超时 | `supervise` 等满 `START_BUDGET = 60s` 仍探不到 |
| 运行期掉线 | 每 10s 一拍，首个探测失败后补拍 3 次（间隔 400ms，单次超时 2.5s），全败判掉线 → 静默 6s → 加载页 + 全端口扫描 30s → 全败进离线页 |
| 恢复失败 | 上述流程走完仍无响应，会 `kill_core` 再重拉 |

也就是说核心要**连续约 36 秒**探活失败才会出这条文案 —— 单次抖动不够。

## 二、修的三处

### 1. 库层没设 `busy_timeout`（最容易咬人的一处）

`node:sqlite` 是全同步 API，默认 `busy_timeout = 0`：另一进程持有写锁时，任何一次写入
**立刻**抛 `SQLITE_BUSY`。而同步层把写入放在一个大事务里，于是表现是「同步失败」；
同一时间健康探测也可能被这条同步写卡住，触发上面那条掉线链。
加 `PRAGMA busy_timeout = 5000`（`server/src/db/index.ts`），把瞬时争用吸收在库层。

### 2. 残留核心没有被清理，且「是不是我的实例」判得太松

`kill_core` 只杀自己 `Child` 句柄里的进程；壳被任务管理器结束 / 崩溃 / 升级替换 exe 时，
核心会活下来。下次启动时新核心抢不到 3001 → 漂到 3002，**同一份 `data/` 上就有两个写者**。
外部 agent（Claude Desktop 等）配置里写死的 `http://127.0.0.1:3001/mcp` 还会一直打到旧的孤儿上。

- `spawn_core` 在拉起前调用 `kill_stale_cores`：按镜像名找 `icpc-core.exe`，
  只清「父进程已退出」的那些（父进程还活着的不动，避免误伤别的窗口/别的安装）；
- `findOurInstance` 从「`sea === true` 即认定」改为 `looksLikeSameInstall`：
  `/api/health` 已回 `dataDir`，必须与自己的数据目录一致。否则**另一份安装**的核心会被
  认成「我已经在运行」，本安装静默退出、页面却指向别人的数据库（用户看到的正是「数据没了」）；
- 桌面壳的 `check()` 补上 `sea === true` 校验（与服务端 `instance-health.ts` 同口径）——
  否则壳可能把窗口挂到一个 `tsx` dev server 上。

### 3. 端口漂移后外部 agent 找不到它

核心允许漂移 20 个端口，而壳的扫描范围只有 3001..3020 —— 默认端口被长期占用时，
核心会落到范围之外，壳就永远探不到（用户双击 `icpc-core.exe` 却一切正常，这正是 issue 里的现象之一）。

- 核心启动后把**实际端口**写进 `data/runtime.json`（含 pid 与启动时刻），退出时删除；
- 壳先读这个文件（且必须探通才采信），再退回原来的范围扫描。

## 三、没做的事，以及为什么

- **没有**改探测预算 / 重试次数：36 秒的容差是刻意的（见 `discovery.rs` 注释里 issue #39 的教训），
  调小只会把「正常卡顿」放大成「莫名重启」。
- **没有**做「按 pid 强制终结」的完整进程管理：涉及跨进程生命周期，需要实测回归，
  与本次要发的几个功能改动风险面不同，留作单独一轮。
- **没有**验证「Claude Desktop 启动会向 3001 打 MCP 工具调用」：这取决于用户自己的
  `claude_desktop_config.json`，本机不存在该配置。若确实是这条链路，本轮的第 1 项
  （`busy_timeout`）与 MCP 并发闸门正好对症 —— 两者都是为了让「忙」不再被当成「死」。

## 四、怎么自查

1. 看 `data/logs/core.log` 与壳日志：有没有 `[shell] 服务掉线` / `核心启动超时` / `清理残留核心 pid=`；
2. 看 `data/runtime.json`：确认核心实际在哪个端口；
3. 任务管理器里是否同时有多份 `icpc-core.exe`（有 = 残留没清干净）。
